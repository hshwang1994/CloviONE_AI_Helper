# UX Writing 규칙 — ClovirAssist

> `PA-RC-0002`(Product Audit)가 지적한 문제: 이 문서가 없어서 문구 결정이 매번 호출부의
> 즉흥 판단으로 갈렸다. 오류 문구 167건 중 회복 경로(`[무엇을 하라]`)를 주는 것은 24건
> (14%)뿐이었고, 같은 문장이 마침표 유무로 동시에 존재했고, 같은 개념에 동사가
> 균등하게 갈렸다(생성 84·등록 72·추가 64·만들 49). 좋은 문구는 이미 이 저장소 안에
> 있었다(`Banners.jsx`의 "대리 보기를 종료하지 못했습니다. 다시 시도해 주세요." 등) —
> 문제는 그 관용이 옆 파일로 전파될 장치가 없었다는 것이다. 이 문서가 그 장치다.
>
> **적용 순서**: UX Writing(이 문서)을 먼저 확정하고, 한국어 자연스러움(humanization)은
> 그 뒤에 적용한다. 순서를 뒤집으면 자연스럽게 다듬은 문장이 다시 규칙과 어긋난다.

## 1. 오류 문구 — `[무엇이 실패했다]. [회복 절].`

두 문장, 마침표로 구분한다. 첫 문장이 실패 사실, 둘째 문장이 사용자가 지금 할 수 있는
행동이다. **"왜"는 있으면 좋지만 필수는 아니다** — 이 저장소의 검증된 사례 대부분도
"왜"까지는 안 담는다. 없어도 되는 경우는 원인이 사용자 행동과 무관하거나(서버 내부
오류) 이미 앞 문장이 원인을 겸하는 경우다(예: "권한이 없습니다."는 실패=원인이 같다).

```
좋음: "대리 보기를 종료하지 못했습니다. 다시 시도해 주세요."
좋음: "다른 곳에서 먼저 바뀌었습니다. 새로고침한 뒤 다시 시도해 주세요."
나쁨(막다른 길): "요청을 처리하지 못했습니다."
나쁨(상태 코드 노출): "요청 실패 (500)"
```

### 회복 절을 고르는 법

재시도가 실제로 의미 있을 때만 "다시 시도해 주세요"를 쓴다. 기계적으로 붙이지 않는다
— 재시도해도 같은 결과가 나오는 실패(401/403/404, 검증 오류)에는 다른 안내를 준다.

| 실패 종류 | 회복 절 |
|---|---|
| 일시적(네트워크·5xx·429·409) | "잠시 후 다시 시도해 주세요." / "새로고침한 뒤 다시 시도해 주세요." |
| 네트워크 자체가 끊김 | "네트워크 연결을 확인한 뒤 다시 시도해 주세요." |
| 인증 만료(401) | "로그인이 필요합니다." — 재시도가 아니라 로그인 화면 이동이 회복 경로다 |
| 권한 없음(403) | "권한이 없습니다." + 필요하면 "관리자에게 문의하세요." |
| 대상 없음(404) | "찾을 수 없습니다." — 이미 삭제/이동됐을 수 있다는 사실을 덧붙이면 더 낫다 |
| 입력 검증 실패 | 어떤 필드가 왜 거절됐는지(서버 `error.details`를 그대로 붙인다 — UX-40) |
| 원인 불명(그 외 전부) | "잠시 후 다시 시도해 주세요." — 최후 수단으로만, 더 구체적인 사유가 있으면 그걸 우선한다 |

### 내부 정보를 노출하지 않는다

CLAUDE.md §3-3(secret 비노출)과 같은 원칙이다. 오류 문구에 파일 경로·스택 트레이스·
원시 예외 클래스명·내부 식별자를 그대로 노출하지 않는다. 문의 대응이 필요하면
`X-Request-ID`(요청 상관 id)를 노출한다 — 이미 `ErrorState`(kit.jsx)가 이 패턴을 쓴다.

## 2. 종결 규칙 — 마침표

문장형 문구(안내·오류·도움말)는 **마침표를 찍는다.** 명사형 라벨(버튼·배지·짧은 상태값)은
마침표를 찍지 않는다.

```
문장형(마침표 O): "권한이 없습니다.", "저장했습니다.", "다시 시도해 주세요."
라벨형(마침표 X): "저장", "취소", "권한 없음"(배지), "대기 중"(상태 배지)
```

**같은 문장을 두 판본(마침표 유무)으로 동시에 두지 않는다.** 발견되면 문장형 쪽(마침표 O)
으로 통일한다 — 화면에 독립된 문장으로 뜨는 문구는 전부 문장형이다.

## 3. 표준 동사표 — 같은 개념은 같은 동사로

같은 "새로 만든다"는 개념에 생성/등록/추가/만들다가 균등하게 섞여 있었다. 아래로
고정한다. **화면에 보이는 문구(라벨·버튼·안내)에만 적용한다** — 코드 식별자(함수명·
변수명·API 필드명)는 바꾸지 않는다(제약사항, 기술 용어는 대상이 아니다).

| 개념 | 표준 동사 | 쓰는 자리 | 쓰지 않는 동의어 |
|---|---|---|---|
| 새 항목을 만든다 | **추가** | 버튼("+ 추가"), 안내("~를 추가하세요") | 생성, 등록, 만들기 |
| 이미 있는 값을 고친다 | **수정** | 버튼("수정"), 안내 | 편집, 변경(단, "역할 변경"처럼 굳어진 개념 명사는 예외) |
| 목록에서 없앤다(복원 가능) | **삭제** | 버튼, 확인 문구 | 제거, 지우기(단, 사용자 입력을 "지우다"는 예외 — 폼 입력 비우기와 구분) |
| 못 쓰게 막는다(복원 가능, 데이터는 남음) | **비활성화** | 버튼, 배지 | 끄기, 중지, 정지(스케줄 실행처럼 진행 중인 것을 멈출 때는 "정지"가 맞다 — 개념이 다르다) |
| 다시 쓰게 한다 | **활성화** | 버튼, 배지 | 켜기, 복원(복원은 "삭제된 것을 되살린다"는 별개 개념) |
| 서버에 저장한다(폼 제출) | **저장** | 버튼("저장"), 토스트("저장했습니다.") | 반영, 적용(단, 설정값을 즉시 반영하는 화면은 "적용"이 맞다 — 폼 저장과 개념이 다르다) |

동사표에 없는 개념을 새로 쓸 때는 이 표에 먼저 추가하고 코드를 따라가는 순서를 지킨다
(재양자화 계열 RC와 같은 원칙 — 규칙 문서를 먼저 고치고 코드가 따라온다).

## 4. 길이

한 문장은 되도록 40자 이내로 쓴다(한글은 영어 단어-수 기준이 그대로 안 맞아, 화면 폭
기준으로 다시 잡았다). 오류 문구 전체(실패+회복)는 되도록 2문장을 넘기지 않는다 — 검증
실패처럼 여러 사유를 한 번에 보여줘야 하면 목록(줄바꿈)으로 늘어놓지 이어붙인 긴 한
문장으로 만들지 않는다.

## 5. 괄호

괄호는 **부가 정보**(단위·기술적 참고값)에만 쓴다. 문장의 핵심 내용을 괄호 안에 숨기지
않는다.

```
좋음: "보내려는 내용이 너무 큽니다."
좋음: "요청이 너무 잦습니다(잠시 후 다시 시도해 주세요)." — 괄호 안이 부가 안내일 때
나쁨: "요청 실패 (500)" — 핵심 정보(무엇이 실패했는지)가 괄호 밖에 아예 없다
```

## 6. 이 규칙이 적용되지 않는 것

- 기술 용어·제품명·상태값·API 필드명·수치의 의미 — 안 바꾼다.
- 짧은 버튼 라벨을 억지로 문학적으로 늘리지 않는다("저장"을 "변경사항을 저장합니다"로
  바꾸지 않는다).
- 로그인 화면(`app/templates_html/login.html`)처럼 이미 승인된 디자인 원본을 그대로
  이식한 문구 — 그 문구는 별도 승인 절차를 거친 것이라 이 문서의 사후 검토 대상이 아니다.

## 7. 기계 검사

`scripts/static_checks.sh`가 이 규칙 중 기계적으로 검사 가능한 것을 못박는다(진행 중 —
`docs/BACKLOG.md` PA-02 참고). 규칙만 두면 다시 갈라진다는 것이 `PA-RC-0002` 자체의
증거다(이미 좋은 문구가 24건 있었는데도 안 퍼졌다).
