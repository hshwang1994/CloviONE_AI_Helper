## alembic — 이식하지 않는다 (D-189)

61 revision 을 PG 에서 재생하지 않는 이유:

| 장애물 | 수 | PG 에서 무슨 일이 |
|---|---|---|
| boolean `server_default=sa.text("0"\|"1")` | **31곳** | 타입 오류 |
| FTS5 virtual table + trigger DDL (0030 · 0050) | 2 revision | PG 에 문법 자체가 없다 |
| **`sqlite_where=` 부분 유니크 인덱스** | **3개** | **`WHERE` 가 조용히 사라져 전체 유니크가 된다** → 승인 재요청 · 프롬프트 2차 버전 · 2회 offboarding 이 막힌다 (R2) |
| `recreate="always"` | 3곳 | PG 에서도 전체 테이블 재작성 |
| 0055 의 전제 | 1 | "SQLite 는 기존 데이터를 새 FK 로 소급 검사하지 않는다"에 **의존**한다 — PG 에서는 거짓 |

→ `alembic/versions/` → `alembic/legacy_sqlite/`(비활성 보관), `0001_pg_baseline.py` 하나로 재시작.

## `VARCHAR(n)` 길이 감사 (S1 · P-04 — 완료, **운영 정본으로 측정**)

> **S2 가 이행했다**: `messages.message_id` 를 `VARCHAR(128)` 로 넓혔다.
> `jobs.message_id`(64)는 감사 결과 **넓힐 필요가 없었다** — `retry`/`regenerate` 가
> `role != user` 를 거부하므로 사용자 메시지 id(≤64)만 들어온다.
> **못 잰 105 컬럼은 그대로 S13 Dry Run 의 「길이 초과 0」이 이어서 본다.**

**선언의 정본은 모델**(`app/models_registry` 의 `Base.metadata`), **실데이터의 정본은 운영
SQLite** 다. `.backup` 무중단 스냅숏을 떠서 재고 스냅숏은 지웠다 — **운영 DB 는 읽기만 했다.**
지문: alembic `0061` · 75 테이블 · 257 인덱스 · `ticket_cache` 1,124 · `document_cache` 110 ·
`search_documents` 1,238 · `messages` 311. 원장은
[`../EVIDENCE/S1/varchar_prod.json`](../EVIDENCE/S1/varchar_prod.json).

### 넘긴 것 하나 — legacy 가 아니라 **지금 코드가 만든다**

| 컬럼 | 선언 | 운영 최대 | 초과 행 | **계약상 최대** |
|---|---|---|---|---|
| **`messages.message_id`** | `VARCHAR(64)` | **80** | **20 / 311** | **108** |

`messages.message_id` 길이 분포(운영 311행): 32~40 이 291행, **75 가 17행, 80 이 3행**.

만드는 자리는 `app/jobs/handlers/chat_message.py` 다.
`:283` 이 `a-{client_message_id}-{job.id}`, `:285`·`:381` 이
`a-{client_message_id}-fail-{job.id}` 를 만든다. `job.id` 는 uuid4 **36자**이고
`client_message_id` 는 **클라이언트가 준다** — `app/chat/router.py:87` 의
`Field(min_length=8, max_length=64)` 와 `app/chat/service.py:33` 의
`^[A-Za-z0-9_-]{8,64}$` 가 상한을 **64** 로 잡는다.

따라서 **관측 80은 우연이고**(지금 클라이언트가 36자 UUID 를 보낸다), 계약이 허용하는
최대는

```
"a-" (2) + client_message_id (≤64) + "-fail-" (6) + job.id (36) = 108
```

**S2 가 써야 하는 숫자는 80 이 아니라 108 이다.** 관측값에 맞추면 클라이언트가 더 긴
(그러나 유효한) id 를 보내는 날 다시 깨진다.

SQLite 는 길이를 무시했으므로 아무 일도 없었다. **PG 에서는 `INSERT` 가 거부된다** —
실 PG16 에 그 두 문자열을 넣어 `value too long for type character varying(64)` 를 재현했다.
즉 Migration 이전에 **이식 직후 런타임 채팅이 깨진다.**

**대응은 «넓힌다» 하나다.** 이 컬럼은 `uq_messages_conversation_message_id` 유니크 키의
일부라 절단하면 키가 깨지고, Exception 으로 빼면 대화가 사라진다.
