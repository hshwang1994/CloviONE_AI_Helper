# PROJECT KEYS — 20건 초안표 (사용자 확인 대기)

> **이 문서는 결정 하나를 기다린다.** 확인이 끝나면 확정표가 되고, 그 뒤로는 바뀌지 않는다.
> 규칙과 근거는 [`MASTER_PLAN.md`](MASTER_PLAN.md) §5.2 · [`../DECISIONS.md`](../DECISIONS.md)
> **D-196 · D-197**. 적용(재채번)은 **S13** 이 한다.

## 왜 사람이 정하는가

**Key 소유는 영구다.** 한 번 쓰인 이름은 `retired` 가 될 뿐 다른 프로젝트로 넘어가지
않는다 — 그것이 `<KEY>-<SEQ>` 가 전역에서 충돌하지 않는 유일한 근거다(D-196). 되돌릴
수 없는 이름을 기계가 짓게 두지 않는다.

`app/work/keys.py::suggest()` 가 초안 후보를 만들 수 있지만, 그 결과는 사람이 읽기
어렵다(브로드컴 → `BRDK`). 아래 표는 **손으로 지은 것**이고, `suggest()` 는 앞으로
새 프로젝트를 만들 때 빈칸을 채워 주는 보조 도구로 남는다.

## 규칙 (§5.2)

2~10자 · 영문 대문자 시작 · 대문자+숫자 · 대소문자 무관 유일 · 예약어 금지 ·
**재사용 금지** · URL 안전.

`GIT` 은 **예약어**다. 옛 티켓 번호가 `GIT-142` 이고 그것은 영구 별칭이라, 어떤
프로젝트가 그 이름을 가져가면 새로 발급한 `GIT-142` 가 옛 것과 같은 문자열이 된다.

## 확인하면 무슨 일이 일어나는가

1. `project_key_registry` 에 20건이 `active` 로 들어가고 `projects.code` 가 채워진다.
2. **그때부터** 새 티켓이 `<KEY>-<SEQ>` 를 받는다. 그 전까지 새 티켓은 번호 없이 만들어지고
   옛 이름(`GIT-n`)으로 불린다 — 그것이 3층 식별자를 두는 이유다(D-195).
3. 기존 1,124건의 재채번은 **S13** 이 한다. 옛 `GIT-n` 은 영구 별칭으로 남아 계속 열린다.

## 확인이 늦어져도 막히는 것은 없다

S6 는 Key 없이도 끝난다. 등록·채번·해석·변경이 전부 동작하고, Key 가 없는 프로젝트의
티켓은 번호를 안 받을 뿐이다(`app/work/service.py::number_if_possible`). 막히는 것은
S13 의 재채번 하나이고, 그것이 D-197 이 「확정 전 재채번 없음」이라고 적은 이유다.
