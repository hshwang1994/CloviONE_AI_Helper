# EVIDENCE / S10 — Retrieval 융합 가중치와 임베딩 모델 재검토

> D-209 는 융합 가중치의 **초기값만** 주고 «최종 가중치는 S10 이 실제 relevance 로 다시
> 정한다 — 여기서 숫자를 지어내지 않는다» 라고 적었다. D-211 은 «S10 이 실제 본문으로
> 다시 재고, 그때 필요하면 모델만 바꾼다» 라고 적었다. 이 디렉터리가 그 둘의 원장이다.

## 🔴 먼저: **업무 본문으로는 못 쟀다**

D-211 의 상향 경로가 전제한 「Notion 본문을 다시 실어 온 뒤」가 **아직 오지 않았다.**
2026-08-23 실측:

| 어디 | `document_cache` 본문 | `ticket_cache` 본문 |
|---|---|---|
| 개발 사본 `var/web.sqlite3` | **0건** | 1건 (38자) |
| 운영 서버 `/var/lib/clovirone-web-assistant/web.sqlite3` | **0건** | 31건 (7,630자) |

Notion 동기화 셋이 전부 실패 상태이고(WORK_STATE 「전환 축 다섯」), 본문이 실려 오는 것은
**S13** 이다. 그래서 「업무 기록으로 쟀다」고 적지 않는다.

## 그래서 무엇으로 쟀는가

**이 저장소의 한국어 문서**(`docs/**/*.md`)다. 사람이 쓴 진짜 한국어 산문이고, 무엇보다
**길다** — S1 의 Corpus 는 중앙값 96자였고 여기는 **705자**다. D-211 이 「다시 재라」고 한
조건 중 길이는 이것으로 충족된다.

| | |
|---|---|
| chunk | **849건** (문서 25개 · 제품 chunker 가 만들었다) |
| chunk 길이 | 중앙값 **705자** · p90 921 · 합계 588 KB |
| 질의 | **600개** — `span` 200 · `infix` 200 · `recall` 200 |
| 임베딩 | 실 모델 `intfloat/multilingual-e5-small` (제품 Adapter 로 만들었다) |

**한계를 함께 적는다**: 기술 문서라 어휘 분포가 티켓·회의록과 다르고, 한 문서
(`docs/DECISIONS.md`)가 chunk 의 66%다 — **주제가 매우 동질적**이라 벡터 레인에게 가혹한
코퍼스다. 절대값이 아니라 **가중치·상한·모델 사이의 비교**로 읽는다.

## 질의 세 종류 — 하나만 쓰면 잘못된 결론이 나온다

`span`(어절 경계 부분구간) · `infix`(**어절 내부** 부분구간) · `recall`(어절을 절반 버리고
순서를 섞은 것). **S10 이 실제로 `infix` 를 빠뜨린 채 한 번 뽑았고, 그때 「FTS 가
트라이그램보다 낫다」는 결론이 나왔다** — D-209 를 정면으로 뒤집는 값이다. 그 질의군을
넣자 이유가 드러났다:

## 결과 1 — 단일 레인 (MRR@10)

| 레인 | 전체 | `span` | `infix` | `recall` |
|---|---|---|---|---|
| `trgm` | 0.5242 | 0.8775 | **0.6600** | **0.0350** |
| `fts` | 0.6601 | 0.9842 | **0.0575** | **0.9387** |
| `vector` (상한 없음) | 0.2187 | 0.1597 | 0.1819 | 0.3144 |

**두 레인이 서로의 빈자리를 메운다.**

* `infix` 에서 FTS 는 **0.0575** 다 — D-209 가 짧은 글에서 잰 recall 0.083 을 긴 본문에서
  그대로 재현한다. PG 의 전문검색은 한국어 어절 내부를 못 본다.
* `recall` 에서 트라이그램은 **0.0350** 이다. **찾기는 하는데 순위를 못 매긴다** —
  `similarity()` 가 질의를 통짜 문자열로 비교하기 때문이다. 낱말 뭉치의 순위는 `ts_rank`
  가 매긴다.

## 결과 2 — 가중치 (MRR@10)

| 조합 | 전체 | `span` | `infix` | `recall` |
|---|---|---|---|---|
| D-209 초기값 (`fts .5` · `vec 1.0`) | 0.7553 | 0.9121 | 0.6781 | 0.6758 |
| **S10 채택** (`fts 1.0` · `vec 0.5`) | **0.8869** | 0.9825 | **0.7423** | 0.9360 |
| 격자 최고 (`ceil .14` · `fts .75` · `vec .5`) | 0.8889 | 0.9867 | 0.7314 | 0.9487 |

**바꾼 것 둘:**

* `w_fts` **0.5 → 1.0.** D-209 는 「FTS 가 찾는 것은 pg_trgm 이 이미 전부 찾으므로 FTS 는
  recall 에 기여할 수 없다」고 적었고 **짧은 제목 글에서는 맞았다.** 긴 본문에서는 아니다
  — `recall` 질의군을 FTS 가 혼자 짊어진다(0.9387 대 0.0350).
* `w_vector` **1.0 → 0.5.** 벡터 가중치만 흔든 값(상한 0.16 · `fts 1.0` 고정):
  `0.0 → 0.8693` · **`0.5 → 0.8869`** · `1.0 → 0.8313` · `1.5 → 0.6781` · `2.0 → 0.6432`.
  **거들 때는 도움이 되고 앞장서면 해가 된다.**

  같은 자리에서 FTS 가중치만 흔들면: `0.0 → 0.6518` · `0.25 → 0.7778` · `0.5 → 0.8549` ·
  `0.75 → 0.8889` · **`1.0 → 0.8869`**. 0.75 와 1.0 은 사실상 동점이고(0.0020),
  D-209 의 0.5 는 그보다 **0.032 낮다**.

격자 최고와 채택안의 차이는 전체 0.0020 이고, 채택안이 **`infix` 에서 더 낫다**(0.7423 대
0.7314) — 한국어에서 가장 어려운 질의군이라 그쪽을 고른다.

## 결과 3 — 벡터 거리 상한 (`VECTOR_MAX_DISTANCE = 0.16`)

최근접 이웃은 **언제나** 답을 낸다. 상한이 없으면 아무 관계 없는 질의에도 근거가 생기고,
그러면 「근거가 없다」가 영원히 성립하지 않는다 — 모델은 매번 상관없는 문서를 근거로 받고
그 답에는 인용 번호까지 붙는다.

값의 근거는 **독립된 측정 둘**이다:

| 출처 | 값 |
|---|---|
| S9 실 모델 (주제가 다른 글) | 질의↔맞는 본문 **0.1151** · 질의↔상관없는 본문 **0.1984** |
| S10 (이 코퍼스) | 정답 chunk 거리 p90 **0.1591** · max 0.1764 |

0.16 은 그 사이를 자르고 참 이웃을 대부분 남긴다.

🔴 **그리고 이 코퍼스가 드러낸 한계를 그대로 적는다**: 주제가 동질적인 코퍼스에서는
정답과 오답의 거리 분포가 겹친다 — 정답 p50 **0.1401**, 최근접 오답 p50 **0.1375** 으로
**오답이 더 가까운 쪽이 절반**이다. 어떤 상한도 그 둘을 못 가른다. 상한이 하는 일은
**주제가 아예 다른 질의를 걸러 내는 것** 하나이고, 같은 주제 안의 순위는 RRF 가 맡는다.

## 결과 4 — 임베딩 모델 재검토 (D-211 상향 경로) → **e5-small 을 그대로 쓴다**

| 모델 | 차원 | 전체 | `span` | `infix` | `recall` | 색인 | 질의 |
|---|---|---|---|---|---|---|---|
| **multilingual-e5-small** | 384 | 0.2187 | **0.1597** | 0.1819 | 0.3144 | **11.7 chunk/s** | **10.5ms** |
| bge-m3 | 1024 | 0.2245 | 0.1366 | **0.2053** | 0.3318 | 1.2 chunk/s | 26.7ms |

D-211 이 걱정한 「긴 문서에서 격차가 커진다」는 **이 길이에서는 안 일어났다.** 전체
MRR 차이는 **+0.0058**(+2.7% 상대)이고 `span` 에서는 오히려 e5-small 이 낫다. 그 대가는
**색인 9.8배 · 질의 2.5배**다. 바꾸지 않는다.

**함께 적어 두는 것 둘:**

1. **색인 처리량이 D-211 의 숫자와 다르다.** D-211 은 120 docs/s 였고 여기는 **11.7
   chunk/s** 다 — 글이 96자에서 705자로 길어진 값이다. S13 이 용량을 계산할 때 쓸 숫자는
   **이쪽**이다.
2. **거리 척도는 모델마다 다르다.** bge-m3 의 정답 거리 중앙값은 0.5247 이고 e5-small 은
   0.1504 다. `VECTOR_MAX_DISTANCE` 는 **모델에 딸린 값**이라 모델을 바꾸면 함께 다시 잰다.

## 레인 지연 (600 질의 · 849 chunk)

| 레인 | p50 | p95 |
|---|---|---|
| `trgm` | 0.99ms | 10.87ms |
| `fts` | 1.02ms | 70.93ms |
| `vector` | 3.39ms | 4.16ms |

벡터 레인이 **가장 안정적**이다(exact 스캔이라 분산이 없다). 키워드 두 레인의 p95 가 긴
것은 `ILIKE '%…%'` 와 `ts_rank` 의 선택도 추정 때문이고, D-209 가 이미 적어 둔 성질이다.

## 다시 만드는 법

```bash
# 1) 개발 기계 — 코퍼스와 질의를 만든다
python scripts/bench/retrieval_corpus.py /tmp/s10bench

# 2) 서버(10.100.64.71) — 실 모델로 벡터를 만든다. 개발 기계에는 onnxruntime 이 없다.
scp -r /tmp/s10bench/{chunks,queries}.jsonl <서버>:~/s10bench/corpus/
ssh <서버> '~/s9verify/venv/bin/python scripts/bench/retrieval_embed.py corpus \
    --model-root ~/s1bench/models --also-bge'
scp <서버>:~/s10bench/corpus/*.tsv /tmp/s10bench/

# 3) 개발 기계 — 실 PG 에 싣고 제품 레인 SQL 로 잰다
python scripts/bench/retrieval_fusion.py /tmp/s10bench \
    docs/platform/EVIDENCE/S10/retrieval_fusion.json
python scripts/bench/retrieval_model_review.py /tmp/s10bench \
    docs/platform/EVIDENCE/S10/model_review.json
```

⚠️ **`retrieval_fusion.py` 는 제품의 레인 SQL(`app/ai/retrieval/query.py`)을 그대로
부른다.** 벤치가 SQL 을 다시 쓰면 측정한 것과 운영이 도는 것이 다른 질의가 되고, 그러면
이 숫자로 정한 가중치는 운영과 상관이 없다.
