## 0. 바꾸기 전의 진실 (BEFORE)

### DNS — 옛 이름은 이미 없다. 이 사실이 계획을 하나 지웠다.
$ nslookup clovirone-ai.gooddi.lab   (개발 머신 → 권위 서버 gooddi-ad01.gooddi.lab)
  *** gooddi-ad01.gooddi.lab can't find clovirone-ai.gooddi.lab: Non-existent domain
$ nslookup clovirassist.gooddi.lab
  Name: clovirassist.gooddi.lab   Address: 10.100.64.71

  W13 런본 2·3·9 단계는 «옛 이름도 함께 서브하는 호환 창» 을 전제한다. 그 전제가
  이미 깨져 있다 — A 레코드가 없으므로 어떤 클라이언트도 옛 이름을 풀 수 없다.
  이중 이름 인증서와 __DNS_ALIASES__ 를 넣지 않은 이유가 이것이다(D-222).

## 3. Exit 조건 — ssl_verify_result=0, 그리고 그것이 **거짓이 될 수 있는지**

  이 설치처의 인증서는 자체서명이다. 그래서 «검증 통과» 는 신뢰 기준점을 함께 줄 때만
  성립한다 — Exit 조건이 처음부터 `curl --cacert` 로 쓰여 있는 이유다.
  기준점: /home/cloviradmin/clovirassist.gooddi.lab.crt (설치 스크립트가 두는 자리)

  # 켜야 하는 쪽 (Known Good)
    /healthz  http=200 ssl_verify_result=0
    /readyz   http=200 ssl_verify_result=0
    /login    http=200 ssl_verify_result=0

  # 빨간불이 나와야 하는 쪽 (Known Bad — 초록이 무엇을 뜻하는지 정하는 것은 이쪽이다)
    기준점 없이       http=000 ssl_verify_result=18   <- 18 = self signed in chain
    이름이 다르면    http=000 ssl_verify_result=1    <- 1 = 검증 실패

  # 80 -> 443 이 요청된 이름을 보존하는가
    HTTP/1.1 301 Moved Permanently
    Location: https://clovirassist.gooddi.lab/

  주의: 개발 머신(Windows)의 curl 은 Schannel 이라 %{ssl_verify_result} 가 실패해도
  0 을 준다 — 그 값으로 판정하면 안 된다. 위 수치는 서버의 curl(OpenSSL 3.0.13)이다.

## 5. 설치 검증 스크립트 — 이제 실제로 검증한다

  예전 `validate-clovirone-web-assistant.sh` 는 healthz/readyz 를 `curl -k` 로 쳤다.
  -k 는 아무것도 증명하지 않는다 — 이름이 어긋난 채로도 계속 [OK] 였다는 뜻이다.
  그리고 이름만으로 자기 서버를 부르고 있었는데, 이 서버의 /etc/hosts 는 그 이름을
  127.0.1.1 로 푼다(호스트명이 clovirassist 로 바뀌면서 생긴 줄). nginx 는 10.100.64.71:443

## 7. P-10a 해소 — 브라우저 프로브가 검증을 켠 채 통과한다 (2026-08-22)

사용자가 인증서를 Windows CurrentUser\Root 에 설치했다.
  Subject=CN=clovirassist.gooddi.lab  Thumbprint=74A367A6E4FFE653115C0DE39D5368B4EDC5B20E

### Chromium — 양방향

    [OK  ] 검증 켠 채 canonical 이름            HTTP 200 · title='로그인 | ClovirAssist'
    [OK  ] 반례 · 인증서에 없는 이름은 막힌다      net::ERR_CERT_COMMON_NAME_INVALID
                                              (--host-resolver-rules 로 wrong.gooddi.lab 을
                                               같은 IP 로 보냈다 — 같은 서버·같은 인증서, 이름만 다르다)

전면 우회가 아니라 **진짜 검증**이다. 그리고 그 오류가 `ERR_CERT_COMMON_NAME_INVALID` 라는
것이 중요하다 — S1 이 「구조적으로 알 수 없다」고 적은 그 실패가 이제 실제로 빨간불이 된다.

### 그 전에 한 번 죽었다 — 신뢰 기준점이 **세 갈래**다

인증서를 운영체제 저장소에 넣은 직후에도 하네스는 이렇게 죽었다:

    [auth] 저장된 비밀번호로 로그인 성공: ui-qa@goodmit.co.kr
    [FATAL] 세션을 만들지 못했습니다: 로그인은 됐지만 /api/me가 인증을 인정하지 않습니다.

TLS 이야기가 한 마디도 없어서 **인증 회귀처럼 읽힌다.** 원인을 갈라 보면:

    NODE_EXTRA_CA_CERTS 없이
        page.goto       : HTTP 200
        context.request : Error: self-signed certificate
    NODE_EXTRA_CA_CERTS 주고
        page.goto       : HTTP 200
        context.request : HTTP 200

`page.goto` 는 Chromium 네트워크 스택(운영체제 저장소)이고 `context.request` 는 **Playwright
드라이버 = Node**(번들 CA)다. 서로 다른 저장소를 본다. `auth.py::_fetch_me` 가 그 예외를
삼켜 None 을 돌려주므로 화면에는 TLS 가 전혀 안 보인다.

고친 곳 둘:
  - `tls.py` 가 검증을 켤 때 `NODE_EXTRA_CA_CERTS` 를 함께 심는다(이미 있으면 존중).
  - `run.py` 가 `from_args()` 로 **값만** 받고 있었다 — 보조 프로브 18개와 달리 혼자
    `apply_default_https_context()` 를 안 불러 기준점이 아무 데도 안 심겼다. 같은 진입점으로.

### 하네스 smoke — `--insecure` 없이

    $ UI_QA_TLS_CA=dist/ops/clovirassist.gooddi.lab.crt python -m scripts.ui_qa.run \
        --base-url https://clovirassist.gooddi.lab --routes smoke \
        --fail-on auth_ok theme_applied console_errors page_errors

    TLS 검증 켜짐 … 신뢰 기준점 …clovirassist.gooddi.lab.crt (파이썬·Node 양쪽에 심었다).
    Chromium 의 페이지 이동은 운영체제 신뢰 저장소만 보므로 그쪽은 설치가 따로 필요하다
    [server] HTTP 200 {"status":"ready"}
    [auth] 저장된 비밀번호로 로그인 성공: ui-qa@goodmit.co.kr
    [OK] 치명 검사 실패 없음 (--fail-on=auth_ok,theme_applied,console_errors,page_errors), 억제 0건

`brand_presence` 는 `public_login` 에서 계속 빨간불인데 이번 변경과 무관하다 —
`--insecure` 로 돌린 전 실행에서도 같았고 `--fail-on` 대상도 아니다(UI 축 소유).

### 세 갈래 정리 (다음 설치처가 쓸 표)

| 누가 | 무엇을 보는가 | 준비 |
|---|---|---|
| 파이썬 `ssl`/`urllib` | OpenSSL 기본 + (Windows 는) 운영체제 ROOT | `UI_QA_TLS_CA` |
| Chromium `page.goto` | 운영체제 신뢰 저장소 **만** | 실행 머신에 인증서 설치 (다른 방법 없음) |
| Playwright `context.request` | **Node 번들 CA** | `NODE_EXTRA_CA_CERTS` — `tls.py` 가 심는다 |

Linux 에서 브라우저 레그를 돌린다면 둘째 줄은 `libnss3-tools` + `~/.pki/nssdb` 다.
