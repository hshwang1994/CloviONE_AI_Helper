# 중복과 충돌 검수 (DUPLICATION_AND_CONFLICT_REVIEW)

같은 기능이 여러 곳에 있다는 사실 자체는 문제가 아니다. 문제는 그것들이 서로 다른 답을 낼 때다.
이번 검수에서 확인한 것은 대부분 후자였다.

## 정책이 화면마다 달랐던 것 (전부 수정)

| 충돌 | 어떻게 갈라져 있었나 | 어떻게 통일했나 |
|---|---|---|
| 주(週)의 정의 | '이번 주'는 오늘~금요일, '다음 주'는 월~금, '지난주'는 월~일. 세 표현이 제각각이라 토·일 마감은 '이번 주'에서 영원히 빠지고 '지난주'에서만 보였다 | `week_range(today, offset)` 하나로 월~일 정의 통일 |
| 완료 제외 | 첫 질문과 후속 질문의 기본값이 달랐다. 같은 문장인데 첫 질문 2건, 후속 1건 | `wants_terminal_statuses()` 가드를 두 경로가 공유. 완료를 명시하면 기본값을 적용하지 않는다 |
| 상태 배지 색 | 채팅은 한국어 라벨 + 하드코딩 hex, 관리자는 영어 enum + 토큰. 같은 상태가 화면마다 다른 색이 될 수 있었다 | 채팅이 관리자와 같은 톤 어휘(neutral/success/warning/error/info)를 쓰고, 색은 디자인 토큰이 정한다 |
| 담당자 표시 | 목록은 이름이 없으면 UUID를 찍고, 그룹 집계는 같은 사람을 '미할당'으로 셌다. 두 화면의 건수가 서로 모순됐다 | `person_label()` 하나로 통일. '미할당'은 담당자가 0명일 때만 |
| 상태 변경 판정 | `detect_target_status`와 `is_update_intent`가 서로 다른 동사 목록을 갖고 있었다 | `_CHANGE_VERB_ALT`를 한 곳에 정의해 두 함수가 공유 |
| 작업을 가리키는 낱말 | 생성 의도는 '티켓'만 알아듣고, 다른 규칙은 '작업/업무/할일'도 알아들었다 | `_WORK_NOUNS` 한 곳에 정의해 모든 규칙이 공유 |
| 그룹 축 어휘 | `extract_group_by`와 담당자 이름 해석이 '별로'를 서로 다르게 해석했다 | `_GROUP_AXES` 공유. 축 표현을 이름 해석보다 먼저 소비 |

## 책임이 두 층에 중복된 것 (기록만, 미수정)

| 중복 | 현재 상태 | 판단 |
|---|---|---|
| 응답 문구 생성이 러너와 n8n 양쪽에 있다 | n8n의 'Notion 변경 결과' 노드가 라벨 맵을 따로 갖고 있어, 러너가 아는 필드('난이도')를 n8n이 몰라 '적용된 값' 표시에서 조용히 빠진다 | 결함으로 기록. 러너가 문구를 만들고 n8n은 전달만 하는 구조가 옳다. 이번 세션 범위를 넘어 보류 |
| 티켓 생성 시 기본 상태 '계획'이 n8n에만 박혀 있다 | Notion 스키마의 기본 상태가 바뀌면 n8n을 고쳐야 한다 | 같은 이유로 보류 |

## 정상적인 복수 진입점 (유지)

- 티켓 조회가 채팅과 관리자 양쪽에서 가능한 것은 사용자 편의다. 내부 로직은 러너 하나를 지난다.
- 프로젝트 지목이 문장 안(NH손해보험 티켓)과 후속 문맥(그 프로젝트) 양쪽에서 되는 것은 자연스럽다.
  `resolve_project` 하나가 두 경로를 처리하고, 새 이름이 문맥을 이긴다는 규칙도 하나다.

## 정리 대상으로 남긴 것

- n8n에 비활성 워크플로가 20개 쌓여 있다(과거 버전과 실험). 활성은 `reuSafmsRzO1tIzX` 하나뿐이다.
  지우지 않았다. 지우는 것이 목적이 아니고, 어느 것이 참고용인지 판단할 근거가 없다. 사용자 확인이 필요하다.
