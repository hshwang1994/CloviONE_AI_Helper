## 1. 이어받은 작업과 그 결말

n8n v7 워크플로를 임포트한 직후, 댓글 프로브가 빈 응답을 내고 실행이 error로 남아 있었다.

원인은 `Notion 변경 결과` Code 노드의 문자열 안에서 줄바꿈이 일어나 생긴 JavaScript 문법 오류였다.
이 노드는 쓰기 경로(생성·변경·댓글)에서만 실행되므로, **조회는 멀쩡한 채 쓰기만 전부 죽어 있었다.**
웹훅은 응답 없이 끝나 사용자에게는 빈 화면으로 보였다.

수정하는 과정에서 더 중요한 것을 배웠다. 수정본을 SQL로 `workflow_entity.nodes`에 직접 넣고 n8n을
재시작해도 옛 코드가 계속 실행됐다. DB를 다시 읽으면 수정본이 보이는데 `n8n export:workflow`는 옛
코드를 내보냈고, 실행 스냅샷에도 옛 코드가 찍혀 있었다. **raw SQL은 n8n 자신의 로딩 경로를 건너뛴다.**
지금부터 워크플로 수정은 n8n CLI로만 하고 검증은 export로 되읽어서 한다. 이 규칙은 메모리에 남겼다.

이어받은 작업은 끝냈다. 티켓 생성, 댓글 작성, 프로젝트 없는 티켓 생성을 라이브에서 실제로 확인했다.

## 3. 무엇이 잘못돼 있었나

거의 모든 결함이 한 뿌리에서 나왔다. **낱말을 문장 어디서든 부분일치시켜 조건으로 삼은 것이다.**

- 티켓 제목의 '완료'가 진행상태를 완료로 뒤집었다(승인 없이 Notion에 기록됨)
- 사람 이름 '남기훈'의 '남' 한 글자가 완료 티켓 조회를 껐다
- 프로젝트 이름에 흔한 낱말 '기능'이 엉뚱한 프로젝트 조건이 됐다
- '결제 문제 관련 티켓'의 '문제'가 상태 '이슈' 필터가 됐다
- '난이도 높은 티켓'이 우선순위 높음 필터가 되어 정반대 데이터를 냈다
- '중간 점검 티켓'의 '중간'이 우선순위 필터가 됐다

결과는 대부분 0건이거나 정반대 데이터였다. **0건에는 오류 표시가 없다.** 사용자는 데이터가 없다고 믿는다.
이것이 이 결함군이 위험한 이유다.

지금은 낱말이 **지시된 위치에 있을 때만** 조건이 된다. 상태는 앵커된 자리에서만, 우선순위는 자기
앵커나 지시 위치에서만, 프로젝트는 우연한 짧은 일치가 아니라 이름의 연속 일치나 한 낱말로만.
한국어는 동사가 뒤에 오므로 마지막 동사가 요청의 정체다.

### 이미지 첨부 여정 (라이브 검증)

검증하려고 실제로 돌려 보니 **내 직전 수정이 첨부를 아예 죽여 놓았다.** 사진은 초안 턴에
올리는데 티켓은 '등록해줘' 턴에 만들어진다. 첨부를 '이번 메시지의 사진'으로 좁힌 탓에 승인
턴에는 사진이 없어 아무것도 붙지 않았다. 옛 코드가 대화 폴더를 통째로 훑은 이유가 이것이었다.

이제 러너가 초안을 만들 때 그 초안이 보고 쓴 화면을 기억하고, 첨부는 그것만 본다.
빨강을 먼저 올려 대화한 뒤 파랑을 올리며 티켓을 만드는 시나리오로 확인했다.
**생성된 Notion 페이지에 파랑 한 장만 붙었다.** 지난 턴의 빨강은 붙지 않았다.
비전 분석부터 원본 첨부까지 전 구간을 실제로 확인했다. (러너 3.28.0)

### n8n staticData와 동기화 경고

재전송 표가 정적 데이터에 쌓이는데, 정적 데이터는 하나의 덩어리라 여기에 쓸 때마다 같은
덩어리에 든 조회 캐시(원본 Notion 페이지 3.8MB)까지 통째로 다시 직렬화됐다. **조회 한 번마다
4MB를 다시 쓰고 있었다.**

재전송을 걸러야 하는 이유는 하나뿐이다. 워커가 같은 메시지를 다시 보냈을 때 티켓을 두 번
만들지 않기 위해서다. 조회를 다시 실행하는 것은 아무것도 망가뜨리지 않는다. 그래서 쓰기
응답만 기억하게 했다. 상한도 500 → 60, 보존도 6시간 → 1시간으로 줄였다.

라이브 확인: 조회 10회가 표에 하나도 쌓이지 않는다. 그러면서 **쓰기 재전송은 여전히 같은
티켓을 돌려주고 두 번 만들지 않는다**(같은 message_id로 등록을 두 번 보내 확인).

동기화 실패 경고는 아무도 읽지 않는 필드에 들어 있었다. 사용자에게 보이는 문장으로 옮겼다.

round13에서 이미 "규칙(정규식/키워드) 기반으로는 두 연속 결함 0에 수렴 불가"라고 결론 냈으므로,
이번엔 개별 키워드를 더 얹지 않고 **fail-safe로 재설계**했다(러너 3.53.0):
- 승인은 보수적으로만 인정(첫 낱말 정확 yes / 정확 조합). 접두 매칭('응답'의 '응')·동작어 '완료'가
  승인 없는 쓰기를 냈기에 제거.
- 부정·연기·물음이 섞이면 절대 승인 아님 — 답만 하거나 되묻고 pending 유지.
- 값 재정의는 승인 대기 중이던 그 티켓에 반영(대상·값을 잃지 않음).

러너 216 테스트 green(신규 16), 옛 3.52.0에서 RED 재확인, 배포·라이브 검증까지 마쳤다.
남은 자연어 꼬리(승인을 놓쳐 안전하게 되묻는 드문 경우)는 KNOWN_LIMITATIONS에 성질만 기록했다 —
잘못된 쓰기(HIGH)는 구조적으로 막았고 남은 것은 되묻기(MED)로 수렴한다.

## 전면 재점검에서 새로 잡은 것

이어받은 작업을 끝낸 뒤, 서버·웹서비스·n8n 전체를 다시 조사했다. 8도메인 병렬 탐지 워크플로를
돌렸는데 **검증 단계가 세션 사용 한도로 중단**돼, 워크플로가 '기각'으로 분류한 37건이 실은 검증이
안 돌아간 미검증 상태였다. 이를 **직접 재현**해 확정한 것만 고쳤다.

가장 무거운 것은 **관리자 콘솔의 JSON 입력이 백엔드 계약과 어긋나 관리자 기능 여러 개가 통째로
동작하지 않던 것**이다. 콘솔은 JSON 필드를 파싱된 '객체'로(비우면 'null') 보내는데:
- 정책 생성·수정은 content를 '문자열'로 요구해 **항상 422** — 정책 관리가 아예 불능이었다(HIGH).
- 선택 JSON을 비우면 null이 dict 검증에 걸려 템플릿·스케줄·문서 생성이 기본값만으로 실패(MED).
- 스케줄 동시성 'queue'·문서 모드 'auto'는 백엔드 미지원 값이라 선택 시 422(MED).
이 넷은 백엔드 코어서(객체/None 수용)와 콘솔 옵션 값 교정으로 고쳤다.

그 밖에 직접 재현해 고친 것: 재시도 성공 뒤에도 실패 안내가 남아 상반된 화면을 보이던 것, 러너
'복제'가 secret 바인딩 생성 게이트를 우회하던 것(보안), 정책 감사 액션이 'policie.create'로 잘못
기록되던 것, 응답 대기 중 대화를 삭제하면 컴포저가 영구히 잠기던 것, 첫 메시지 연타로 대화가 2개
만들어지던 것, 템플릿 이름 충돌이 500(→409)이던 것, 사용자 역할 변경 시 함께 보낸 이름·부서가
유실되던 것, operator에게 작업 재시도·취소 버튼이 숨겨지던 것, 403 응답 본문이 소진돼 서버
오류 메시지가 사라지던 것. 사용자 문서(ADMIN/USER_GUIDE)의 낡은 안내(섹션 수, 상단바 메뉴,
응답 대기시간)도 정정했다.

전부 재현 → 수정 → 회귀 테스트(신규 12건) → 플랫폼 전체 업그레이드 2회로 배포했고, 배포 파일
해시가 테스트한 코드와 일치함을 확인했다.
