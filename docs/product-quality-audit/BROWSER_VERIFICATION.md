# 브라우저 실화면 검증 (BROWSER_VERIFICATION)

2026-07-16, 실제 Chrome에서 확인했다. 코드 추적이 아니라 화면에서 본 것이다.

## 어떻게 검증했나

로그인 폼에 비밀번호를 입력하는 일은 하지 않는다. 그래서 인증이 필요한 화면은
**프로덕션 오리진에서 실제 배포된 자산(chat.css, chat.js, admin.css, admin/*.js)을 그대로 불러**
화면을 구성하고, API 응답만 통제해서 확인했다. CSP(`script-src 'self'`)와 실제 CSS 토큰이
그대로 적용되는 조건이다. 서버에는 아무것도 남기지 않았다(검증 후 잔여물 0 확인).

로그인 화면은 인증이 필요 없으므로 프로덕션 화면을 그대로 봤다.

## 채팅 화면

수정 전에는 아래 세 가지가 전부 '아무 일도 없는 것처럼' 보였다.

| 확인한 것 | 결과 |
|---|---|
| 카드 번호 (2페이지) | **11, 12** — 본문 목록 번호와 일치. 수정 전에는 1, 2로 어긋나 그 번호로 누른 '상세'가 거부됐다 |
| Notion에서 열기 링크 | **두 카드 모두 표시**, href가 실제 `app.notion.com` 주소. 수정 전에는 링크가 전부 사라져 있었다 |
| 상태 배지 | 진행 = success 톤, 검증 = warning 톤. 색이 디자인 토큰에서 나온다 |
| 원탭 선택 버튼 | **"프로젝트 목록 보기" 표시**. n8n이 choices를 떨어뜨려 이 기능이 통째로 죽어 있었다 |
| 서버 오류 중 전송 (500) | 상태에 "대화를 불러오지 못했습니다 (오류 500)" + "다시 연결" 버튼. **전송 버튼 잠김 해제**(수정 전 영구 잠김), 폴링 2회 후 정지(수정 전 무한) |
| 대화 목록 로드 실패 (503) | 빨간 안내 "대화 목록을 불러오지 못했습니다 (오류 503). 대화는 지워지지 않았습니다." + "다시 불러오기" |
| 대화 0건 | 안내 "아직 대화가 없습니다. 위의 새 대화 버튼으로 첫 대화를 시작해 보세요." (오류 표시 아님) |

오류 화면과 빈 화면이 이제 명확히 구분된다. 수정 전에는 두 화면의 DOM이 문자 그대로 같았다.

### 검증 중 발견해서 고친 것

메시지 시각 자리에 **"Invalid Date"**가 찍혔다. `created_at`을 읽지 못하면 그 문자열을 그대로
화면에 옮긴다. 못 읽은 값을 사용자에게 시각인 것처럼 보여주면 안 된다. 읽지 못하면 비운다.

## 관리자 콘솔

| 확인한 것 | 결과 |
|---|---|
| 정렬 헤더 접근성 | `th[aria-sort]` + 안에 진짜 `<button>`(tabIndex 0). 키보드로 정렬 가능 |
| 정렬 상태 통지 | 클릭할 때마다 aria-sort가 ascending ↔ descending으로 바뀌고 행 순서도 실제로 바뀐다 |
| 정렬 범위 정직성 | **"정렬은 지금 보고 있는 20건 안에서만 적용됩니다. 전체 137건을 기준으로 정렬한 순서가 아니며, 다른 페이지의 행은 포함되지 않습니다."** 수정 전에는 전체를 정렬한 것처럼 보였다 |
| 모달 레이블 | 6개 필드 전부 `label[for]`가 입력과 연결됨 (스크린리더가 읽는다) |
| 모달 통지 | `role="dialog"`, `aria-modal="true"` |
| 모달 포커스 이동 | 열리면 첫 입력으로 포커스가 들어간다 |
| Escape 닫기 | 동작 확인 |
| 포커스 트랩 | 마지막 요소에서 Tab을 눌러도 모달 안에 머문다 (수정 전에는 뒤쪽 표로 빠져나갔다) |
| 사용자 추가 설명 | "비워두면 임시 비밀번호가 자동으로 생성되어 한 번만 표시됩니다. 직접 정하면 그 비밀번호로 바로 로그인할 수 있습니다." |

## 모바일 드로어 — 1차 관측(2차 재디자인으로 아래 화면은 사라졌다)

> **주의(2026-07-16 정정):** 이 절은 **잉크 사이드바 시절(1차)**의 관측이다. 그 뒤 2차
> 재디자인에서 드로어가 상단바 아래를 통째로 덮는 오버레이로 바뀌면서 아래 수치가 전부
> 낡았다. 헤더를 드로어 위로 띄우던 z-index 45 층은 **제거됐다**(그 층이 열린 드로어의 첫
> 메뉴를 덮어 못 누르게 하던 결함 때문 — `DESIGN_CONSISTENCY_REVIEW.md`의 "드로어가 열리면
> 첫 메뉴를 누를 수 없던 문제"). 지금의 실제 값(CSS 소스 기준, chat.css·admin.css 확인):
>
> | | 1차(아래 기록) | 지금 |
> |---|---|---|
> | 닫힘 transform | `translateX(-260px)` | `translateX(-100%)` |
> | 드로어 색(라이트) | 잉크 | **흰 면**(`--sidebar-bg` = `--color-card`) |
> | 헤더 층 | ☰ 헤더 z-index 45 > 드로어 40 | 헤더 층 없음. 드로어 40 > 백드롭 35 |
> | 닫는 수단 | ☰ 헤더 탭 포함 | 백드롭 탭 · Escape · 대화/메뉴 선택 |
>
> 이 값들은 CSS 소스에서 읽은 것이고 브라우저에서 다시 렌더해 본 것은 아니다. 아래 1차
> 기록은 지우지 않고 남긴다 — 시점을 명시하는 편이 낫다는 이 저장소의 원칙대로다.

**[1차 기록] 닫힘 `translateX(-260px)` / 열림 `translateX(0)`**를 실제 렌더된 계산값으로 봤다.
스크린샷에서 잉크색 드로어와 백드롭, 그 위에 뜬 ☰ 헤더(z-index 45 > 40)를 확인했다.

여기까지 오는 데 세 번의 오독이 있었고 **셋 다 측정 도구가 원인이었다**(제품이 아니었다):
CSP `style-src 'self'`가 `about:blank` iframe에 상속돼 대조군의 인라인 스타일까지 막았고,
창을 줄여도 뷰포트가 안 바뀌어 미디어 쿼리가 발동하지 않았으며, 배경 탭은 CSS transition을
돌리지 않아 열린 상태가 계속 −260으로 읽혔다. CSP 없는 로컬 서버(:8902)에 실제 배포 CSS를 얹고
420px iframe으로 진짜 모바일 뷰포트를 만든 뒤 `transition: none`을 주입하자 정확한 값이 나왔다.
자세한 경위는 `DESIGN_CONSISTENCY_REVIEW.md`에 있다.

## 확인 못 한 것

- **인증된 프로덕션 화면 자체**: 위 검증은 실제 배포 자산 + 통제된 응답이다. 실제 로그인 세션으로
  본 것은 아니다. 로그인 폼에 비밀번호를 입력하는 일은 하지 않기 때문이다.
  사용자가 직접 확인하려면 로그인 후 30초면 된다: 채팅에서 "내 티켓 보여줘" → 카드에
  'Notion에서 열기' 링크와 번호가 보이는지, 관리자 콘솔에서 사용자 표 헤더를 눌러 정렬 안내가
  보이는지.
