# n8n 워크플로에 필요한 변경 (이 저장소에서는 고칠 수 없는 것)

플랫폼(이 저장소) 쪽 준비는 끝나 있다. 남은 것은 n8n 워크플로가 우리가 보내는 값을
읽는 것뿐이고, 그건 여기서 할 수 없다.

---

## 문제

n8n 으로 나가는 POST 자체에는 멱등성 보장이 없다. 그래서 이런 일이 생긴다.

```
우리 워커  ──POST──▶  n8n  ──▶ Notion 에 티켓 생성 (성공)
                       │
                       └── HTTP 응답이 유실 (타임아웃/네트워크)
우리 워커  : 실패로 판단 → 재시도
우리 워커  ──POST──▶  n8n  ──▶ Notion 에 티켓 **또** 생성
```

사용자는 같은 티켓 두 장을 받는다. 그리고 조용히 일어난다 — 우리 로그에는
"재시도 후 성공"으로만 남는다.

중복을 실제로 막는 결정은 **쓰기를 수행하는 쪽**, 즉 n8n 에서만 할 수 있다.

---

## 지금 n8n 이 하고 있는 것

`docs/n8n/…v7.json` 의 '요청 전처리'가 `identity | conversation_id | message_id` 를
열쇠로 `processedMessages` 를 뒤진다. 즉 **중복 판정은 이미 하고 있고**, 열쇠에
`message_id` 가 들어 있다.

주의: n8n 은 우리가 보내는 **`idempotency_key` 필드를 읽지 않는다**
(그 워크플로 파일 전체에 그 이름이 없다).

---

## 플랫폼이 보내는 것

요청 본문에 `idempotency_key` 를 싣는다. 값은 **메시지에서만 파생**되므로,
같은 메시지에 대한 모든 재전송에서 동일하다.

```json
{
  "requester":       { "user_id": "…", "email": "…", "name": "…" },
  "message":         "내 할당 티켓 보여줘",
  "conversation_id": "…",
  "message_id":      "h0123…",
  "idempotency_key": "chatmsg:h0123…"
}
```

| 상황 | `idempotency_key` |
|---|---|
| 최초 전송 | `chatmsg:{message_id}` |
| 워커 재시도 (응답 유실 등) | **같은 값** |
| 사용자가 화면에서 '다시 시도' | **같은 값** |

### 사용자 재시도에서도 값이 같아야 하는 이유 (바꾸지 말 것)

한 번 "사용자 재시도는 새 요청이니 키도 새로 발급하자"고 바꿨다가 되돌렸다.
틀린 방향이었다.

**재시도는 오직 '실패한' 메시지에만 열려 있다** (`app/chat/service.py::retry_message`
가 그 외에는 409). 그런데 메시지가 실패로 보이는 경우에는 두 가지가 섞여 있다:

- n8n 이 정말 아무것도 안 만들었다 → 재시도가 그때 만든다. (문제 없음)
- **n8n 은 티켓을 만들었는데 응답만 유실됐다** → 키가 같아야 저장된 응답이 돌아와
  티켓이 한 장으로 남는다. 키를 새로 발급하면 **두 번째 티켓이 생긴다.**

즉 키를 새로 발급하면, 막으려던 중복 생성을 재시도가 가능한 유일한 상황에서
오히려 더 잘 일으킨다. "사용자가 다시 눌렀는데 옛 답변이 온다"는 걱정은 성립하지
않는다 — 성공한 메시지에는 재시도 버튼이 아예 없다.

이 동작은 `tests/integration/test_chat_ticket_routing_contract.py` 가 못 박고 있다.

---

## n8n 이 해야 할 일 — 한 가지

**중복 판정 열쇠에 `idempotency_key` 를 쓰라.** 지금의
`identity | conversation_id | message_id` 를 그대로 둬도 동작은 같지만,
`idempotency_key` 하나로 바꾸면 열쇠 조립 규칙이 플랫폼과 n8n 두 곳에 흩어지지 않는다.

1. 워크플로 진입점에서 `idempotency_key` 를 읽는다.
2. 이 키로 **이미 완료한 실행이 있으면** 쓰기(티켓 생성 등)를 다시 하지 말고,
   그때 만든 결과를 그대로 응답한다(현재의 `duplicate: true` 응답 형태 그대로).
3. 없으면 평소대로 처리하고 결과를 그 키에 묶어 저장한다.

보관 기간은 **24시간이면 충분하다.** 우리 워커의 재시도는 그보다 훨씬 짧은 창에서
끝난다(`max_attempts=3`).

> ⚠️ **실패 응답은 저장하지 마라.** 실패까지 키에 묶어 두면 사용자가 '다시 시도'를
> 눌러도 저장된 실패가 계속 돌아와 영원히 복구할 수 없다. 저장은 성공한 결과만.

### 대상 워크플로

채팅 메시지를 받는 웹훅(운영에서 `n8n_chat_webhook_url` 설정이 가리키는 것).
문서 자동 생성(`document_generate`)은 이미 같은 규약으로 `idempotency_key` 를 받는다 —
그쪽 구현을 참고하면 된다.

---

## 확인 방법 (각 30초)

**① 중복 쓰기가 막히는가**
n8n 워크플로에서 응답 직전에 일부러 지연을 넣어 우리 쪽 타임아웃을 유발한다
(`n8n_timeout_seconds` 보다 길게). 워커가 재시도한 뒤 **Notion 에 티켓이 한 장만**
생겼는지 본다. 두 장이면 중복 제거가 안 걸린 것이다.

**② 사용자 재시도가 복구되는가**
n8n 을 잠깐 내려 채팅 요청을 실패시킨 뒤, n8n 을 되살리고 화면의 '다시 시도'를 누른다.
정상 답변이 오면 통과다. 계속 실패가 돌아오면 **실패 응답까지 키에 저장**하고 있는
것이다(위 경고 참조).
