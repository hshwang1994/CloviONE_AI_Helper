# n8n 워크플로에 필요한 변경 (이 저장소에서는 고칠 수 없는 것)

이 문서는 **n8n 쪽에서 해야 하는 일 하나**를 적는다. 플랫폼(이 저장소)에서 할 수 있는
준비는 전부 끝났고, 남은 것은 n8n 워크플로가 우리가 보내는 값을 읽는 것뿐이다.

---

## 문제

n8n 으로 나가는 POST 에는 원래 멱등성 수단이 없었다. 그래서 이런 일이 생긴다.

```
우리 워커  ──POST──▶  n8n  ──▶ Notion 에 티켓 생성 (성공)
                       │
                       └── HTTP 응답이 유실 (타임아웃/네트워크)
우리 워커  : 실패로 판단 → 재시도
우리 워커  ──POST──▶  n8n  ──▶ Notion 에 티켓 **또 ** 생성
```

사용자는 같은 티켓 두 장을 받는다. 그리고 이건 조용히 일어난다 — 우리 로그에는
"재시도 후 성공"으로만 남는다.

**두 번째 함정**: 이걸 막겠다고 `message_id` 로 중복 제거하면 반대쪽이 깨진다.
사용자가 실패 메시지를 보고 '다시 시도'를 누른 경우도 `message_id` 가 같기 때문에,
n8n 이 중복으로 판단해 **옛 답변을 그대로 돌려준다.** 사용자는 다시 시도했는데
아무것도 안 바뀐 화면을 본다.

즉 두 경우가 같은 문자열을 쓰는 한, n8n 이 무엇을 하든 한쪽은 틀린다.

---

## 플랫폼이 이미 해 둔 것

요청 본문에 **`idempotency_key`** 를 싣는다. 값은 job 행의 키를 그대로 쓰며,
두 경우가 자동으로 갈린다.

| 상황 | `idempotency_key` |
|---|---|
| 최초 전송 | `chatmsg:{message_id}` |
| 워커 재시도 (응답 유실 등) | **같은 값** — 같은 job 행이라 변하지 않는다 |
| 사용자가 '다시 시도' | `chatmsg:{message_id}:retry:{시각}` — 새 job 행이라 새 값 |

요청 본문 예:

```json
{
  "requester":       { "user_id": "…", "email": "…", "name": "…" },
  "message":         "내 할당 티켓 보여줘",
  "conversation_id": "…",
  "message_id":      "h0123…",
  "idempotency_key": "chatmsg:h0123…"
}
```

이 동작은 테스트로 고정돼 있다 — `tests/integration/test_chat_idempotency_key.py`.
(고치기 전 코드로 되돌리면 '사용자 재시도' 테스트가 실패하는 것까지 확인했다.)

---

## n8n 이 해야 할 일 — 한 가지

**`idempotency_key` 문자열 하나로 중복 제거하라.** 다른 판단 로직은 필요 없다.

1. 워크플로 진입점에서 `idempotency_key` 를 읽는다.
2. 이 키로 **이미 완료한 실행이 있으면**, 쓰기(티켓 생성 등)를 다시 하지 말고
   그때 만든 결과를 그대로 응답한다.
3. 없으면 평소대로 처리하고, 결과를 그 키에 묶어 저장한다.

저장 기간은 **24시간이면 충분하다.** 우리 워커의 재시도는 그보다 훨씬 짧은 창에서
끝난다(`max_attempts=3`).

> 왜 이것만으로 두 경우가 갈리는가: 워커 재시도는 **같은 키**라 2번에 걸려 중복 쓰기가
> 안 생기고, 사용자 재시도는 **다른 키**라 3번으로 가서 정상적으로 다시 처리된다.
> n8n 이 "이게 워커 재시도인가 사용자 재시도인가"를 판단할 필요가 없다.

### 대상 워크플로

채팅 메시지를 받는 웹훅(운영에서 `n8n_chat_webhook_url` 설정이 가리키는 것).
문서 자동 생성(`document_generate`)은 이미 같은 규약으로 `idempotency_key` 를 받는다 —
그쪽 구현을 그대로 참고하면 된다.

## 확인 방법

n8n 쪽 변경 후, 다음 두 가지를 실제로 해 보면 30초 안에 판별된다.

**① 중복 쓰기가 막히는가**
n8n 워크플로에서 응답 직전에 일부러 지연을 넣어 우리 쪽 타임아웃을 유발한다
(`n8n_timeout_seconds` 보다 길게). 워커가 재시도한 뒤 **Notion 에 티켓이 한 장만**
생겼는지 본다. 두 장이면 아직 중복 제거가 안 걸린 것이다.

**② 사용자 재시도가 여전히 새 답을 주는가**
채팅에서 실패를 만든 뒤(예: n8n 을 잠깐 내림) 화면의 '다시 시도'를 누른다.
n8n 을 되살린 상태에서 **새 답변이 오면** 정상이다. 옛 답변이 그대로 오면 ①의
중복 제거가 너무 넓게 걸린 것이다 — 키의 `:retry:` 부분까지 포함해 비교하고 있는지
확인하라.

---

## 이 저장소에서 더 할 수 있는 것은 없다

플랫폼은 안정적인 키를 보내는 것까지가 할 수 있는 전부다. 중복 쓰기를 실제로 막는
결정은 **쓰기를 수행하는 쪽**, 즉 n8n 에서만 할 수 있다.
