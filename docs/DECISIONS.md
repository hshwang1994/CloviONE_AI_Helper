### D-54. Workflow(병렬 서브에이전트)의 산출물도 **직접 diff 리뷰 없이는 안 믿는다**

사이클 3에서 위생 묶음(11단계) 10개 항목을 Workflow 도구로 병렬 서브에이전트 10개에 위임했다
(파일이 서로 안 겹치는 독립 항목이라 격리 없이 병렬 실행). 각 에이전트는 자기 몫의 회귀
테스트를 쓰고 통과를 보고했지만, **그 보고를 그대로 믿지 않고 10개 diff 전부를 직접 읽었다**
— [[probe-false-positives-first]](memory 참조: 자작 프로브·서브에이전트 결과는 표본 확인
전엔 안 믿는다)와 같은 원칙을 Workflow 산출물에도 그대로 적용한 것이다.

그 리뷰에서 실제 결함 1건을 잡았다: 강조색 계정별 저장 구현이 `ThemeModeProvider`에 `userId`
prop을 기대하도록 짜였는데, 그 컴포넌트는 실제 앱 트리에서 `AuthProvider` **바깥**에 마운트돼
있어 그 prop이 **영원히 채워질 수 없는 구조**였다. 에이전트가 쓴 단위 테스트는 그 컴포넌트를
직접 렌더하며 prop을 주입해서 통과했을 뿐 — **"단위 테스트가 통과한다"와 "실제 화면에서
그 배선이 닿는다"는 다른 사실**이고, 후자를 증명하는 배선 테스트(`user-menu-accent-wiring.test.jsx`,
실제 `<UserMenu>` + 실제 `<ThemeModeProvider>` 조합으로 렌더)가 없었다면 이 결함은
`실환경검증완료`는커녕 다음 감사 라운드까지 조용히 남아 있었을 것이다 — 정확히 이 저장소가
반복해서 찾아낸 "헬퍼는 있는데 부르는 쪽이 안 부른다" 결함 패턴을, 새로 짠 코드 자신이
재현할 뻔한 사례다.

**적용**: 병렬 서브에이전트/워크플로를 쓸 때 (1) 자기 몫 안에서만 판단하게 하고 파일 스코프를
명시적으로 좁혀 겹치지 않게 하면 격리(worktree) 없이도 안전하게 병렬화할 수 있다, (2) 그래도
합치기 전에 코디네이터가 diff를 전부 읽는다, (3) "새 함수/컴포넌트가 실제 호출부에서
도달 가능한가"는 특히 의심한다 — 단위 테스트가 prop/인자를 직접 주입하면 실배선 여부를
가려 버린다.

### D-53. 자율 연속 실행은 하네스 기본 기능(`/loop` dynamic mode)을 쓴다 — 별도 Supervisor를 새로 만들지 않는다
Sonnet 구현 단계 진행 중 사용자가 "Claude 응답 하나가 끝나도 사용자 입력 없이 다음 사이클이
자동으로 이어지는 자율 실행 구조를 만들고 검증하라"고 요청했다. 프로젝트 안에 이미 있는
유사 구조(워크플로·큐 등)를 먼저 찾았으나 **그 요청이 뜻하는 것(Claude Code 세션 자체의 연속
실행)에 해당하는 것은 애플리케이션 코드가 아니라 실행 하네스 쪽에 이미 있었다** — `/loop`
스킬(간격 없이 부르면 self-paced dynamic mode)과 `ScheduleWakeup` 도구가 정확히 이 목적으로
설계돼 있다: 한 턴이 끝나도 하네스가 예약된 시각(또는 백그라운드 작업 완료 이벤트)에 **사용자
입력 없이** 같은 세션을 다시 불러 이어가게 한다.

**그래서 새 Python/bash Supervisor를 프로젝트에 만들지 않았다.** 이유:
1. 사용자 지시 자체가 "기존 구조가 있으면 먼저 찾아 재사용하라"고 명시했고, 이게 그 구조다.
2. 자체 제작 Supervisor(예: `claude` CLI를 재귀 호출하는 셸 스크립트)는 이 실행 환경의 세션·
   인증·컨텍스트 모델과 독립적으로 동작해 중복 세션이나 상태 불일치를 만들 위험이 있다.
   하네스 내장 메커니즘은 **같은 세션·같은 컨텍스트**를 이어간다.
3. 이미 실측으로 검증됐다 — 사이클 1 종료 후 `ScheduleWakeup` 으로 예약된 재개가 사용자 입력
   없이 두 차례 이상 실제로 발동해 사이클 2(SYS-01/SEC-30/FN-40/OPS-10/OPS-11)와 SEC-22 추가
   구현까지 전부 그 재개만으로 이어졌다(대화 기록에 사용자 메시지 없이 `<task-notification>`
   만으로 여러 사이클이 진행됨).

**동작 방식**: 매 사이클 끝에서 `ScheduleWakeup`을 호출해 다음 깨어날 시각(주로 완료 대기 중인
배경 작업의 폴백 하트비트, 1200~1800초)과 재개 프롬프트(`/loop <원 지시>`)를 남긴다. 배경에서
돈 `Bash(run_in_background:true)` 작업이 끝나면 `<task-notification>` 이 그 자체로 즉시 재개
신호가 된다(예약 시각을 기다릴 필요 없음). 이 저장소의 실제 완료 기준(§0, `실환경검증완료`만
완료)을 실제로 충족하기 전까지는 `ScheduleWakeup({stop:true})`을 부르지 않는다 — 부르는 순간
루프가 끝나므로, 그건 최종 완료 판정에서만 쓴다.

**한계**: 이 메커니즘은 **현재 세션이 열려 있는 동안만** 유효하다(브라우저/터미널을 닫으면
끊긴다). 세션이 끊겨도 이어져야 하는 요구라면 `/schedule`(클라우드 cron)이 맞는 도구이지만,
이번 요청은 "지금 이 작업을 사용자 입력 없이 끝까지"이므로 세션형 `/loop` 로 충분하다고 판단했다.

### D-05a. QA 하네스는 SSH 터널이 아니라 **HTTPS 를 직접** 겨눈다 (`--insecure`)
처음엔 자체서명 인증서를 피하려고 `ssh -L 8081:127.0.0.1:8080` 터널로 http 를 쓰려 했다.
**되지 않는다.** 서버가 `COOKIE_SECURE=true`(확인함)라 세션 쿠키에 `Secure` 가 붙는데,
Playwright 의 `context.request`(APIRequestContext)는 http 로 `Secure` 쿠키를 **싣지 않는다**.
브라우저 페이지 쪽은 `127.0.0.1` 을 신뢰 컨텍스트로 봐서 통과하지만 API 클라이언트는 더 엄격하다.
증상은 "로그인은 됐지만 `/api/me` 가 인증을 인정하지 않습니다" 로만 나와 원인이 안 보인다
(같은 흐름을 curl 로 하면 200 이라 서버 문제가 아님이 드러난다).

그래서 하네스에 `--insecure` 를 넣었다 — `urlopen` 프로브에 `ssl._create_unverified_context()`,
모든 `new_context()` 에 `ignore_https_errors`. **터널은 쓰지 않는다.** 부수 효과로 nginx 경유
경로(gzip·헤더·프록시 타임아웃)까지 실제로 검사 대상이 된다.

## 디자인 시스템

### D-06. 공통화 ≠ 동일화
공통화의 목적은 전부 똑같이 보이게 하는 것이 **아니라**, **같은 의미·같은 용도의 UI는 같은 규칙을
따르고 다른 의미·다른 중요도는 적절한 시각적 차이를 갖게** 하는 것이다. 따라서 양방향으로 움직인다:
- **합친다**: 의미가 같은데 구현이 다른 것 — 표 3벌, 툴바 9개, 빈 상태 8벌, 챗 버블 5벌
- **분리한다**: 의미가 다른데 이름·구현이 같은 것 — `kit.jsx:917 Drawer = Modal`(6곳은 중앙
  다이얼로그, 2곳은 진짜 사이드 드로어)

**페이지별 예외 CSS를 더 쌓지 않는다.** 반복되는 문제는 토큰·Variant·Size·Layout 규칙과 공통
컴포넌트 자체를 고친다.

### D-07. 시각적 위계를 제품 규칙으로 고정한다
```
페이지 제목 → 설명·상태 → 주요 콘텐츠 → 주요 Action → 보조 Action → 위험 Action
```
화면만 봐도 이 관계가 읽혀야 한다.

### D-08. Button은 액션 의미로부터 Variant를 설계한다 (하드코딩된 이름을 이식하지 않는다)
현재는 4종뿐이고 **기본값이 `outlined`라 평범한 버튼까지 테두리 상자**가 되며, `primary`와 `danger`가
**둘 다 `contained`**라 위험이 주요와 같은 무게다. 표 내부 액션 표현이 없고 `loading` 상태도 없다.
→ 제품의 실제 액션(주요 실행 / 저장 / 보조 / 이동·링크 / 조회 / 표 내부 인라인 / 위험)을 전수조사한
뒤 필요한 Variant·Size·상태(hover/focus/active/disabled/loading)를 **그 결과로부터** 정한다.
특정 Variant 이름을 미리 정해 두고 맞추지 않는다.

### D-09. Typography는 정보 계층을 표현한다 — 화면에서 `fontWeight`를 직접 쓰지 않는다
지금 `fontWeight`가 65파일에 8종 값으로 흩어져 있고 **≥700이 148회**다. 역할별 계층
(페이지 제목 / 섹션 / 카드 제목 / 본문 / 라벨 / 보조설명 / 숫자 / 상태)에 크기·굵기·색을 배정하고
`variant`로만 쓰게 한다. **모든 숫자와 제목을 굵게 하지 않는다.**

### D-10. 색은 의미다 — `resolveChartColor` 패턴을 시스템 규칙으로 승격한다
시맨틱 색 계약(정상·정보·주의·위험·비활성)을 정의하고 전 제품이 그것만 쓴다.
**단순 숫자·일반 콘텐츠에 강한 색을 쓰지 않는다.** "숫자 강조"와 "상태 강조"를 구분한다.

### D-11. Card는 역할별 유형을 갖는다
지금은 `Card`+`StatCard` 둘뿐이라 숫자가 있으면 무조건 크게·굵게 처리된다.
→ Metric / Status / Summary / Warning / Action / Content의 실제 역할을 분석해 강조 단계를 설계한다.
판단 기준은 **"지금 행동해야 하는 정보인가, 단순 현황인가"**다.

### D-12. 화면 크기·데이터 개수에 따라 변해야 할 것은 고정값이 아니라 규칙으로 만든다

### D-13. CSP는 되돌리지 않는다 — 문서를 정정한다
`app/core/middleware.py`의 CSP는 2026-08-04 **사용자 지시로 의도적으로 완화**됐다

`CLAUDE.md` §2-6이 아직 옛 문구(`script-src 'self'`)를 유지하고 있으므로 **코드가 아니라 문서를

## AI 도우미

### D-14. 스트리밍은 sync 제너레이터 `StreamingResponse`(SSE)로 한다
불변규칙 #1이 `async def` 핸들러를 금지한다. FastAPI는 **sync 제너레이터**를 `StreamingResponse`에
넣으면 스레드풀에서 돌리므로 불변규칙을 지키면서 SSE가 가능하다. 러너 쪽은
`claude -p --output-format stream-json`으로 바꾼다.
**왜 필요한가**: 지금은 `subprocess.run`이 전체 출력을 블록하고 브라우저가 1.5초 폴링을 하므로 답이
통째로 튀어나온다. 진행 표시도 불리언 하나에서 나오는 가짜다.

### D-15. 대화 이력의 소유권을 플랫폼으로 가져온다
지금 플랫폼은 이력을 **0건** 보내고(계약 테스트가 `"context" not in body`로 못박음) 연속성이 전적으로
러너의 별도 SQLite에 있다. 그 결과 (a) 모델 기억이 8턴×1000자로 제한되고 (b) **규칙엔진 턴이 이력에
안 들어가 대화에 구멍이 나며** (c) 대화를 지워도 러너 사본이 안 지워진다
(`clear_persisted_context` 호출 0회 — 프라이버시 결함).
플랫폼에 이미 `messages` 테이블이 있으므로 이력을 여기서 만들어 보내고, 요약 기반 압축을 넣고,
삭제를 러너까지 전파한다.

### D-16. 타임아웃 사다리를 바깥이 안쪽보다 길게 뒤집는다
현재 플랫폼 180s < n8n 240s라 **플랫폼이 먼저 포기하고 동일 본문을 재전송**하는데 중복 쓰기 방지는
n8n 휘발성 메모리에만 있다(재시작 시 소멸). 우리가 보내는 `idempotency_key`를 n8n은 읽지도 않는다.
→ 플랫폼 > n8n > 러너 순으로 정렬하고, 멱등키를 n8n이 실제로 읽게 한다.

### D-17. 러너 호출은 레지스트리를 경유한다
`app/runners/*`는 CRUD·enable/disable·health·rollback UI가 완비인데 실제로 러너를 부르는 두 기능은
`settings.game_runner_url`·`assistant_runner_url`을 **직접 읽어 레지스트리를 우회**한다 —
화면에서 base_url을 바꿔도 아무 일도 안 일어나는 **죽은 조작판**이다.
채팅은 같은 함정을 피하려고 워크플로 레지스트리를 경유하고 그 이유가 코드에 적혀 있다
(`jobs/handlers/chat_message.py:33-38`). 러너도 같은 처리를 한다.
**이것을 AI 플래그를 켜기 전에 한다** — 안 고치고 켜면 기능만 켜지고 조작판은 여전히 죽어 있다.

### D-18. 드로어를 전체화면 채팅의 표현층 위로 통합한다
드로어는 `useChat`의 **상태기계만** 재사용하고 표현층을 다시 만들어, 티켓 카드·링크·선택지 칩·실패
표시·재시도·복사를 전부 버리고 단일 행 IME-무방비 컴포저를 쓴다. 클로비 버튼 3개 중 2개가 이리로
가는데도 그렇다. → `Message`/`RichText`/`CardStack`/알림 배너를 공유시킨다.
**순서**: 디자인 시스템(D-06~D-12)을 먼저 정리한 뒤에 통합한다. 반대로 하면 두 번 일한다.

## 조사 방법

### D-23. `position: fixed` 겹침은 스크린샷으로 판정하지 않는다
`full_page=True` 스크린샷은 fixed 요소를 뷰포트 좌표대로 캔버스에 **한 번만** 그린다. 6,000px
페이지에서는 그것이 우연히 어떤 표 행의 버튼 위에 찍히고, 나는 그것을 결함으로 7번 기록했다가
전부 철회했다. 살아 있는 DOM(`elementsFromPoint`)으로 재니 60라우트 중 1건, 긴 표 8종 ×
스크롤 4위치에서 **0건**이었다. **하네스의 `fab_overlap`은 내내 옳았고 나는 정확한 검사가
통과한 것을 PNG 로 반박했다.** 도구: `scripts/ui_qa/fab_occlusion.py`. 상세는 QA_COVERAGE §9-6.

### D-24. 상태를 갖는 기능은 화면이 아니라 **대화·실행**으로 검증한다
`/chat` 은 70라우트 캡처에서 매번 정상으로 찍혔다. 그런데 두 턴을 이어서 물어보니 11일 전
중단된 티켓 생성 모드가 무관한 질문을 납치했다(`AI-30`). 캡처를 아무리 늘려도 안 나온다.
**대조 실험**(같은 문장, 문맥만 다름)이 원인을 가르는 데 결정적이었다 — 이 패턴을 재사용한다.
도구: `scripts/ui_qa/ai_e2e.py` · `ai_probe.py` · `ai_verify.py`.

### D-25. "구현됐다"와 "한 번이라도 돌았다"를 분리해 센다 (`U` 축)
화면은 **기능이 없는 것**과 **아무도 안 쓴 것**을 똑같이 그린다. 프로덕션 DB 행 수로만 갈리고,
실측 결과 **12개 기능의 실행 이력이 0**이었다(`USE-01`). `U`가 `-`인 기능은 다른 축이 아무리
`O`여도 신뢰하지 않는다 — 테스트와 화면은 있는데 실환경에서 한 번도 돌지 않은 코드다.

### D-26. 라우트 커버리지는 **역할 커버리지와 곱해야** 의미가 있다
`system_admin` 전용 4화면을 `admin` 계정으로 찍으면 4장 모두 권한 거부 화면이 되고, 21개 검사가

실행 계정이 볼 수 없는 라우트는 `ok`가 아니라 `권한부족(미검사)`로 집계해야 한다.
이 4화면을 실계정으로 다시 찍자 **그 4개에서만 새 결함 18건**이 나왔다.

### D-27. 내 도구가 "실패했다"고 말해도 결과를 직접 확인한다
AI E2E 첫 실행에서 내 말풍선 선택자가 틀려 3턴 모두 **"전송되지 않음"으로 보고**됐다. 서버에
저장된 메시지를 읽어 보니 **3턴 모두 정상 전송·응답**이었고, 거기서 이 조사의 가장 큰 발견
(`AI-30`)이 나왔다. 도구의 실패 보고를 제품의 결함으로 옮겨 적었다면 정반대의 결론을 남길 뻔했다.

### D-28. 서버가 오늘에야 HEAD 가 됐다 — "데이터가 없다"를 결함으로 읽지 않는다
라운드 9~14가 **2026-08-08 오전까지 미배포**였다. 그래서 그 이전에 만들어진 프로덕션 데이터는

### D-29. 화면이 아니라 **업무 흐름**으로 한 번 더 감사한다
`ADM-01`(잠금 해제가 웹 0회 / CLI 13회)의 원인은 결함 하나가 아니라 **개별적으로 모두 옳은
결정 다섯 개의 조합**이었다 — 자동 해제(옳음) + 알림에 body 없음 + `user` 딥링크 제외(규칙으로는
옳음) + `locked` 필터 없음 + "관리자에게 문의하세요"(친절함). 화면 단위 감사로는 영원히 안 보인다.

**규칙: 알림에서 시작해 완료까지 실제로 눌러 보는 흐름 감사를 별도로 한다.**
대상: 계정 잠금 해제 · 비밀번호 재설정 · 온보딩 · 오프보딩 · 티켓 배정 · 문서 생성 요청 ·
승인 처리 · 백업 확인. 각 흐름의 판정 기준은 "화면이 열리는가"가 아니라
**"알림을 받은 사람이 SSH 없이 끝낼 수 있는가"**다.

### D-30. 무엇이 실제로 쓰이는지는 `audit_logs` 가 이미 알고 있다
42종의 action 별 집계가 "사람들이 무엇을 하고 무엇을 피하는가"를 그대로 보여 준다
(`cli.*` vs 웹 액션 대비가 `ADM-01` 의 출발점이었다). 그런데 제품 안에서는 그렇게 읽히지 않는다 —
`/audit` 은 시간순 목록일 뿐 액션별 집계가 없다(`ADM-04`). **조사할 때는 DB 를 직접 집계하고,
제품에는 그 뷰를 넣을지 따로 판단한다.**

### D-31. 사람에게 UUID 를 옮겨 적게 하지 않는다
최소 3곳에서 제품이 이름을 알면서 사용자에게 식별자 받아쓰기를 시킨다 —
`DGEN-01`(문서 생성 모달의 필수 `워크플로 ID` + `템플릿 ID` + `원본 Notion DB`),
`USE-04`(`/schedules` 의 `대상 ID` 열이 워크플로 UUID 링크),
`UA-22`(`documents/router.py:78-87` 이 만들어 둔 `requested_by_name` 을 화면이 안 쓰고 UUID 를 그림).
**규칙: 참조를 입력받을 때는 선택 목록(이름 표시 + id 전송)을 기본으로 하고, 표에는 이름을
그린다. 자유 입력은 목록이 너무 커서 검색이 필요한 경우에만, 그때도 자동완성으로 한다.**

### D-32. 빈 상태의 기준 두 개 — `/documents` 와 `/my-tickets`
`DS-14`(빈 상태 8벌)를 통일할 때 새로 설계하지 않는다. `/documents` 의 빈 상태가
**전제조건 · 실패 코드(409) · 확인할 화면 · 기대 결과 · 막혔을 때 갈 곳**을 모두 담고 있고,
`/my-tickets` 미연결 빈 상태가 **삽화 + 제목 + 번호 단계 + 기대 결과**를 담고 있다.
`/games`(`GM-02`·`GM-03`)처럼 "버튼 두 번 + 무엇을 할 수 있는지 없음"인 것들을 이쪽으로 맞춘다.

### D-33. 표→카드 전환은 **뷰포트 상수**가 아니라 **표가 필요한 폭**으로 판단한다
`TABLE_CARD_BREAKPOINT = "(max-width:899.95px)"`(`kit.jsx:415`) 하나가 28개 레지스트리 표
전부를 지배한다. 그래서 **768 에서는 카드로 잘 바뀌는데 1024 에서는 표를 유지해 셀이
1~6자짜리 세로 기둥으로 무너진다**(`RESP-01`, 실측). 4열 표와 9열 표에 같은 숫자를 쓸 수 없다.
**`DataTable` 이 자기 필요 폭을 재서 넘칠 때 카드로 바꾼다.** 카드 레이아웃 자체는
**이미 있고 잘 동작한다** — 새로 설계하지 않는다([D-22](#)).

### D-34. `V`(반응형) 축은 **경계가 아니라 경계 사이**를 본다
기존 뷰포트 목록이 768 → 1366 으로 건너뛰어 **그 사이를 한 번도 보지 않았고**, 가장 심한
결함이 정확히 그 구간(1024)에 있었다. 앞으로 반응형 실행은 최소
**768 / 1024 / 1200 / 1366** 네 폭을 함께 돌린다.

### D-35. 대비는 **렌더된 색**으로 재고, 못 재는 곳은 못 잰다고 말한다
`theme_applied` 는 다크 클래스 유무만 본다 — **읽히는가**는 아무도 안 봤다(`CTR-05`).
`scripts/ui_qa/contrast.py` 로 잰다. **그라디언트 배경은 `backgroundColor` 로 알 수 없으므로
판정을 포기하고 그 개수를 함께 보고한다** — 그냥 지나치면 상단바 흰 글씨가 흰 body 위로
계산돼 1.07:1 위양성이 쏟아진다(첫 판에 실제로 그랬다). **보고된 위반 수는 언제나 하한선이다.**

### D-36. 강조색은 **사용자가 고르므로** 선택지마다 대비를 보장해야 한다
`primary.main` 은 라이트·다크에 **같은 hex** 로 쓰인다(`theme.js:185`). 흰 배경에서 통과하는
색이 어두운 표면에서 3.6 언저리로 떨어지고, 고를 수 있는 4색이 **전부** 다크에서 미달이다
(`CTR-03`). 다크용 파생값을 두거나(이미 `primaryStrong`·`primary.light` 가 그렇게 한다)
선택 시점에 대비를 검증해야 한다 — **색 고르기는 취향이지만 읽히는 것은 요건이다.**

### D-37. **빈 상태와 오류 상태는 다른 상태다** — 같은 화면을 쓰면 안 된다
API 가 실패했을 때 이 제품은 **「담당한 티켓이 없습니다」·「프로젝트가 없습니다」·「아직 대화가
없습니다」** 를 보여 준다(`FAIL-01`, 실측). 잘 만든 빈 상태가 오류 경로에서 **흉기**가 된다 —
사용자는 데이터가 사라진 것으로 읽고, 「'미할당 티켓'에서 맡을 일을 고르라」 같은 **틀린 행동**을
권유받는다. **성공했지만 0건**과 **알 수 없음**을 코드에서 갈라야 하고, 화면도 갈라야 한다.

### D-38. `200 + 비JSON` 을 성공으로 취급하지 않는다
프록시 중간 페이지·SSO 리다이렉트·WAF 차단면은 전부 `200 + HTML` 이다. 실측에서 이 경우가
**정직한 500 보다 나쁘게** 처리됐다 — 8화면 전부 재시도 버튼이 사라지고 **콘솔 오류조차 0건**이라
실패 흔적이 남지 않는다(`FAIL-02`). 이 제품엔 이미 이력도 있다(`n8n 응답이 올바른 JSON이 아닙니다`).
**응답 파싱 실패는 네트워크 실패와 같은 등급으로 다룬다.**

### D-39. 오류·로딩 상태는 **주입해서** 검증한다
서버를 망가뜨리지 않고 브라우저 라우트 가로채기로 `500 / abort / 200+HTML / 지연` 네 가지를
만들 수 있다(`scripts/ui_qa/failure_states.py`). 정상 경로만 보면 **"콘솔 오류 0건"** 같은
결론이 나오는데, 실패 경로에서는 화면당 최대 5건이었다(`FAIL-05`). **강점 주장에는 어느 경로에서
관찰한 것인지 붙인다.**

### D-40. 표 문제는 화면 28개가 아니라 `DataTable` **한 곳**에서 고친다
같은 근본 원인이 서로 다른 두 트리거로 드러났고, **둘 다 셀 폭 51px 로 측정됐다** —
① 뷰포트가 좁을 때(`RESP-01`, 1024) ② 값이 길 때(`HOST-01`, 문서 폭 5,271px).
열 폭이 **순수하게 내용에서 파생**되므로 한 열이 길면 다른 열이 짜부라진다.
`kit.jsx:498-502` 가 이미 경고를 적어 뒀다. 필요한 것 세 가지 —
**① 열 폭 제약(비율 또는 최소/최대) ② 긴 값 절단(`truncateCol` 은 이미 있다, 안 쓰일 뿐)
③ 표가 필요한 폭을 넘으면 카드로 전환**([D-33](DECISIONS.md)). 화면마다 고치면 28번 고치고
29번째에서 다시 생긴다.

### D-41. 적대적 데이터는 **주입해서** 본다 — 서버 데이터는 늘 얌전하다
지금 서버의 제목은 짧고 목록은 작고 문자는 한글·영문뿐이라, **70라우트를 몇 번 찍어도**
긴 값·이상한 문자 문제는 안 나온다(`HOST`). 응답 가로채기로 `long / many / weird` 를 주입한다
(`scripts/ui_qa/hostile_data.py`). 실측 결과 **"많은 데이터"(200행)는 약점이 아니었고**
**"긴 데이터"가 치명적**이었다 — 추측으로는 순서를 못 정한다.

### D-42. 포커스 표시는 **합성 후 대비**로 판정한다 — 알파 틴트는 대비가 아니다
포커스 표시가 `rgba(0,0,0,0.12)` 처럼 알파 틴트뿐이면, 색 문자열만 보고는 보이는지 알 수 없다.
**배경 위에 합성한 뒤** 배경과의 대비를 재야 한다. 실측: 사이드바 남색 위에서
**1.05(라이트) / 1.45(다크)** — WCAG 1.4.11 기준 3:1 의 3분의 1이다(`KBD-01`).
그리고 **라이트가 더 나쁘다** — 사이드바는 두 모드 모두 어두운데 라이트 규칙이 검정을 덧칠한다.
`tokens.css:39` 가 이미 전역 링이 2.76 이라 미달임을 적어 뒀다 — **알고 있었지만 재보지 않았다.**

### D-43. vanilla → MUI 이관에서 **포커스 링이 빠졌다** — 클래스 목록으로 확인한다
`screens.css`·`global.css` 에 `:focus-visible { outline: 2px solid … }` 가 **12개 vanilla
클래스**에 정확히 붙어 있는데 MUI 컴포넌트에는 없다(`KBD-03`). 이관 작업이 스타일을 옮길 때
`:hover` 는 옮겼고 `:focus-visible` 은 놓쳤다. **MUI 테마 한 곳(`theme.js`)에 넣으면 전 화면에
적용된다** — 화면마다 고칠 일이 아니다([D-40](DECISIONS.md) 과 같은 형태).

### D-44. 새 프로브의 첫 결과는 **위양성으로 가정하고** 표본을 하나씩 확인한다
이번 세션에 자작 프로브가 **네 번** 틀렸고 **네 번 다 "결함이 있다"는 방향**이었다 —
① 전체 페이지 스크린샷이 `position:fixed` 를 엉뚱한 자리에 그려 겹침을 지어냄(7건 철회)
② 그라디언트 배경을 못 읽어 상단바 흰 글씨를 1.07:1 로 계산(전부 철회)
③ 「건너뛰기 링크 없음」 — 정규식이 실제 문구 「본문 바로가기」를 놓침
④ MUI 의 숨은 `MuiSelect-nativeInput` shim 을 "라벨 없는 입력"으로 셈(14건 철회).

**규칙**: 새 프로브가 위반을 내면 **기록하기 전에** ① 표본 2~3개를 개별 덤프해 실제 속성을 보고
② 가능하면 눈으로(스크린샷·클립) 확인하고 ③ 코드에서 의도된 설계인지 grep 한다.
**측정 도구를 만든 사람이 그 도구의 첫 희생자다.**

### D-45. 공용 규칙은 **기본값**이어야 한다 — 옵트인이면 조용히 빠진다
저장소에 토큰·헬퍼·등록표가 **이미 다 있는데** 12곳에서 안 걸려 있었다(워크플로 `R1`, 2건 직접 검증).
`EmptyState` 에 `KO_WORD_BREAK` 한 줄이면 **31개 파일**이 동시에 좋아지고, `ROUTE_OWNER` 2줄이면
High 1건이 사라진다. 실패가 **조용해서**(증상이 없어 리뷰에서 안 걸림) 새 화면마다 재발한다.
**테스트도 "특정 컴포넌트"가 아니라 "사용자 산문을 그리는 모든 컴포넌트" 단위로 건다** —
`ko-wordbreak.test.jsx` 가 `Callout` 만 본 것이 이 사태의 원인이다.

### D-46. 사용자 문자열 검사망이 **코드만** 보면 DB·시드는 영원히 빠져나간다
`check_user_text.py` 가 소스만 스캔하므로, 한 번 DB 에 들어간 문자열은 규칙을 어겨도 계속 표시된다 —
소스는 콜론인데 화면은 금지 글리프 em 대시인 실물이 있다(`R2`). 검사 대상을 **API 응답 페이로드와
시드·마이그레이션 값**까지 넓힌다. 그리고 **기계가 파싱하는 문자열을 사용자에게 보여 주지 않는다**
(`app/admin/feature_flags.py:100` 이 설명 문자열을 파싱한다 — 문구만 고치면 계약이 깨진다).

### D-47. 판독은 **혼자 하지 않는다** — 반증률 58%가 그 값어치다
미판독 40화면을 6그룹 병렬 판독 + 그룹별 적대적 반증으로 돌렸더니 **175건 중 102건이 폐기**되고
73건이 남았다. 혼자 판독했으면 그 102건이 그대로 들어갔을 것이다(내 단독 판독에서도 이번 세션에
4건의 위양성이 나왔다, [D-44](DECISIONS.md)). **반증자에게는 "의도가 코드에 명시돼 있는지 grep 하라"고
지시하는 것이 핵심이다** — 폐기 사유의 다수가 "코드에 이유가 적혀 있음"이었다.

### D-48. 한 파일에서 못 찾았다고 **제품에 없다**고 말하지 않는다
`RET-02`("보존 정책이 제품 전체에 없다")를 `worker_main.py` grep 한 번으로 단정했는데,
실제로는 `app/core/retention.py` 가 **10개 표를 1시간마다** 정리하고 있었다(대화 365일·알림 90일·
잡 60일·스케줄런 60일·메일 90일·휴지통 7일·리셋토큰·잡첨부 24시간·유실티켓·고아업로드).
살아남은 것은 **`sessions` 하나뿐**이었다(`RET-01R`).
**부재를 주장하려면 ① 기능 이름으로 grep ② 도메인 모듈 디렉터리 확인 ③ 설정 레지스트리 확인
세 가지를 다 한 뒤에 한다.** "있다"는 한 번 찾으면 증명되지만 **"없다"는 훨씬 비싸다.**

### D-49. 감사 로그 집계는 **시간 분포**와 **내 흔적 제외** 없이 해석하지 않는다
`ADM-01`("관리자가 웹 대신 SSH 를 쓴다")을 액션별 건수만 보고 단정했고, `WORK_STATE` 최상단에
올린 뒤 서사와 우선순위까지 그 위에 세웠다. 재검증자가 **타임스탬프**를 뽑자 CLI 기록은
**설치 초기 온보딩 1회분(2026-07-15~16)** 이었고, 늘어난 4건은 **이번 조사가 만든 QA 계정**이었다.
올바른 결론은 "웹이 외면당했다"가 아니라 **"아직 일상 운영 데이터가 없다"**였다.
**규칙: 로그 집계에는 반드시 ① 시간 분포 ② 조사자 자신의 흔적 제외 ③ 표본 기간이 대표적인가
를 함께 본다.** 데이터가 적을수록 집계는 서사를 잘 만들어 낸다.

### D-50. 서버만 보고 "기능이 없다"고 하지 않는다 — 프런트에 폴백이 있을 수 있다
`NOTI-04`("알림 103건 중 딥링크 3건")는 서버의 `destinations.py` 만 보고 낸 결론이었다.
프런트에 **폴백 표**(`NotificationBell.jsx:33-44` `OBJ_ROUTE`/`OBJ_ID_PARAM` +
`serverRoute(n) || objRouteHref(...)`)가 따로 있어 실제로는 **94/97 이 이동 가능**했다.
`D-48`(한 파일에서 없다고 제품에 없다고 하지 않는다)의 **계층 버전**이다 —
**한 계층에서 없으면 반대 계층을 본다.**

### D-51. 적대적 데이터는 **일어날 수 있는 모양**으로 주입한다
`HOST-01` 의 문서 폭 5,271px·셀 51×2,353px 는 **응답의 모든 문자열을 동시에 300자로** 바꿔서 나온
값이다 — 현실에서 불가능하다. 수치는 진짜지만 **달성 가능한 값이 아니다.**
**규칙: 한 필드만 현실적으로 길게(제목 100~200자) 하고 enum·날짜·ID 는 그대로 둔다.**
과장된 입력은 근본 원인(열 폭 제약 부재)을 바꾸지 않지만 **심각도 판단을 망친다.**

### D-52. 조사에서도 자격증명을 명령행에 두지 않는다 — 특히 **서브에이전트에게 넘기지 않는다**
이 세션에서 `ssh … "echo 'PW' | sudo -S …"` 형태를 반복했고, 워크플로 프롬프트에 같은 비밀번호를
적어 **서브에이전트 13개에게 배포**했다. `sudo -S` 로 stdin 을 쓴 것은 맞지만 `echo` 인자가 평문이라
**로컬·원격 셸 히스토리, 프로세스 목록, 대화 기록** 네 곳에 남는다 — `CLAUDE.md` §2-4 가 막으려던
바로 그것이고, §10 이 이미 "대화에 노출된 SSH 비밀번호 변경"을 미결로 적어 둔 상태였다.

**규칙**: ① 서버 접근이 필요한 조사는 **내가 실행하고 결과만** 에이전트에게 준다
② 질의는 한 번에 묶어 호출 수를 줄인다 ③ 조사 종료 시 원격 히스토리 정리를 안내한다
④ **노출된 자격증명은 손상된 것으로 취급하고 회전을 요청한다.**
"제품의 보안 규칙"은 조사자에게도 적용된다 — 나는 이 규칙을 **제품에서 검사하면서 내가 어겼다.**

### D-53. 작업 단위를 BACKLOG 항목 번호에서 **제품 영역(MEGA CYCLE)**으로 바꾼다
Cycle 4 배치 1~6(2026-08-10)은 "관련 항목 4~5개 고치기 → 전체 pytest → 배포 →
Chrome 몇 개 확인 → 문서 갱신 → 다음 4~5개"를 반복했다 — 품질은 높았지만(22건 전부
revert-to-verify 통과, 배포 6회 전부 `UPGRADE_OK`), BACKLOG 전체(522건) 대비 진행이
너무 느렸다(약 8%). 그리고 배치가 CORE/UA 같은 "작은 인프라 이슈" 카테고리에 머무는
동안, `docs/WORK_PLAN_INDEX.md` §3이 명시한 원래 순서(디자인 시스템 → AI 도우미 →
관리자 IA → 기능/권한 E2E)에서 1~3단계를 건너뛰었다(`docs/PROGRESS_STATUS.md` §5-1
에서 이미 지적함).

**바뀌는 것**: 작업 단위가 "BACKLOG 항목 하나"에서 "제품 영역 하나(MEGA CYCLE)"로
바뀐다. 하나의 영역 안에서는 관련 있는 모든 것(공통 컴포넌트·같은 파일·같은 상태
머신·같은 사용자 흐름)을 넓게 조사해서 한 번에 대량으로 고치고, 그 영역이 사실상
끝날 때까지 계속한다. 검증은 위험도에 따라 계층화한다 — Critical/Security/RBAC/
데이터손실/동시성/마이그레이션/권한상승만 이 세션의 revert-to-verify 전부를 적용하고,
단순 UI/레이아웃/문구는 회귀 테스트 + 실제 브라우저 확인으로 충분하다. 배포는 영역
전체가 끝난 뒤 한 번, 그 뒤 Chrome 검증도 그 영역이 건드린 라우트 전체를 본다(빈
데이터·많은 데이터·오류·권한거부·반응형·라이트/다크 포함).

**안 바뀌는 것**: 품질 기준 자체(테스트 없이 커밋 금지, 위험한 변경은 revert-to-verify,
실환경검증과 구현완료를 구분해서 정직하게 기록, 사용자 승인 없이 진행하는 자율 루프)는
그대로다. "크게 간다"가 "덜 검증한다"의 핑계가 되면 안 된다.

**첫 MEGA CYCLE**: A — AI Assistant / 러너 대화 엔진(`runner/claude-work-assistant/
assistant.py`, 5,890줄). `RN-01`~`RN-14`(24건 다수가 이 파일)와 `AI-30`(Critical —
11일 전에 중단된 CREATE 플로우가 무관한 질문을 납치)이 전부 이 한 파일의 상태
머신(대화 컨텍스트에 만료가 없음·검사 순서 버그·락 처리)에 뿌리를 둔다는 것을 조사로
확인했다 — 공통 원인 하나로 다수 항목을 끝낼 수 있는 전형적인 사례. `FAIL-01`
(Critical — 빈 상태와 오류 상태가 같은 화면)은 공용 UI kit 컴포넌트(`frontend/src/ui/
kit.jsx`)가 근본 원인이라 이 사이클이 아니라 다음 Design System 사이클로 배정한다
(Critical이라 순서상 그 다음으로 당긴다 — 미루는 게 아니라 순서 배정).

### D-54. MEGA CYCLE의 기준은 "몇 건 처리했나"가 아니라 "제품 영역이 거의 끝났나"다
D-53 전환 후에도 실제 작업 단위가 다시 작아지는 경향이 나타났다(같은 제품 영역의 후속
작업 C/D/E/F를 각각 별도 MEGA CYCLE로 쪼개고, 매번 전체 테스트→배포→Chrome 검증을
반복). 사용자가 명시적으로 교정: **MEGA CYCLE의 종료 기준은 Backlog 처리 건수가 아니라
해당 제품 영역/서브시스템이 실질적으로 거의 끝났는가다.** 같은 제품 영역의 후속 작업(같은
Design System이면 토큰 몇 개·컴포넌트 3개·dead CSS 등)을 각각 쪼개지 말고 하나의 큰
MEGA CYCLE 안에서 계속 처리한다. 구현 중에는 변경 영역과 직접 관련된 focused test만
반복하고(frontend-only 변경에 backend full suite를 매번 돌리지 않음, 그 역도 마찬가지),
Full 회귀(backend+frontend+static+build)·배포·광범위 Chrome E2E는 그 제품 영역이 배포
가능한 큰 단위로 충분히 완성됐을 때 한 번 수행한다. 건수 제한은 인위적으로 두지 않는다
(한 사이클에 20~100건 이상도 가능). Critical/Security/RBAC/데이터손실/마이그레이션/
동시성 또는 즉시 실환경 확인이 필요한 고위험 변경은 이 배칭 예외로 그대로 즉시·개별
처리한다. **적용 예**: MEGA CYCLE G(관리자 IA)가 이 지시 직후 IA-01/IA-02 2건만 고치고
끝내려던 것을 대신 FN-13·IA-04·RG-11까지 같은 사이클 안에서 넓혀 처리하고 마지막에
한 번만 전체 회귀·배포·Chrome 검증을 수행했다.

### D-55. Backlog ID 중복을 지울 때 "파일에서 나중에 나온 쪽"이 자동으로 "틀린 쪽"은 아니다
`AI-*` 항목 15개가 세 차례의 서로 다른 조사 라운드에서 번호를 재사용해 중복돼 있었다
(예: `AI-30`이 서로 무관한 두 항목 — Critical CREATE 하이재킹과 Med screen_context —
에 동시에 쓰였고, `AI-31`·`AI-37`도 각각 2개씩이었다). 1차 수정에서 "파일에 두 번째로
나오는 occurrence"를 기계적으로 새 ID로 옮겼는데, 이것이 **틀렸다** — `docs/WORK_STATE.md`
의 MEGA CYCLE A 절과 `docs/DECISIONS.md`(D-53 포함) 자체가 이미 "AI-30 Critical"·
"AI-37"을 구체적인 하나의 finding으로 여러 번 인용하고 있었고, 그 인용이 가리키는
실체는 file상 두 번째 occurrence(즉 내가 새 ID로 옮기려던 쪽)였다. **교훈**: 중복 ID를
해소할 때는 raw file 순서가 아니라, `WORK_STATE.md`·`DECISIONS.md`·`PROGRESS_STATUS.md`
같은 다른 load-bearing 문서가 그 번호를 이미 특정 finding으로 인용하고 있는지 먼저
grep으로 전수 확인하고, 인용이 있는 쪽의 번호를 보존한 채 인용이 **없는** 쪽만 새 번호로
옮긴다. 이번엔 `AI-30`(Critical, 되돌림)·`AI-31`(의도분류, 되돌림)·`AI-37`(탈출어 안내,
되돌림) 3건이 이 방식으로 걸렸고, 밀려난 3건은 각각 `AI-66`·`AI-67`·`AI-68`로 이동했다.
부수적으로, 재확인 과정에서 `AI-30`(Critical)과 `AI-66`(구 AI-30 Med, screen_context)이
실제로는 **둘 다 MEGA CYCLE A에서 이미 고쳐졌는데** BACKLOG.md 상태 칸이 "발견"으로
방치돼 있던 것도 함께 드러나 바로잡았다(코드 재확인 후 각각 구현완료/부분구현으로 갱신).
